# LLP 0057.000: WinterTC and the platform families — the surface beyond v1, its packaging, and the lanes

**Type:** Plan
**Status:** Draft
**Systems:** Rust Stdlib, Host ABI, CapSec, Platform, Engine, Build
**Author:** Claude (Fable 5.1) for Charlie Cheever
**Date:** 2026-09-03
**Related:** LLP 0057 (the RFC this plans: §2 the three categories, §3.1 the Rust/JS split, §5.2 the two consumers, OQ2 answered *in, whole*), LLP 0059 (the v1 surface — a ceiling measured from Exact 1; §7 the growth rule; this document restates the ceiling against WinterTC), LLP 0059.000 (§3.9 `crypto`, §3.12 `WebSocket`, §3.14 `crypto.subtle`, §3.15 SQLite, §5 the standing exclusions), LLP 0067 (§2 the five families and the two specified after them; §3 the check; §8 how a family is added), LLP 0068 (`Host`, `endow`, `Bindings`; §2 synchronous; OQ1 the crate boundary, OQ3 async), LLP 0069 and LLP 0070 (the fourth and fifth bindings — the pattern every family below follows), LLP 0058.000.000 §8 (one FIFO of admitted host tasks), exact2 LLP 1027 (accepted 2026-09-03: D9 ibex in three, D10 the pure tier as Rust bindings, D1a `fetch` as the normal thing), snapback LLP 1003 §1 (what an effect may use), the WinterTC Minimum Common Web Platform API (https://min-common-api.proposal.wintertc.org/), the Expo SDK module catalog (https://docs.expo.dev/versions/latest/)

## Summary

Charlie asked two things on 2026-09-03: *"In ibex2, it seems like we probably
want to implement WinterTC in Rust? And then also some other things like a way
to access the filesystem, securestore, a few other things. What does that list
look like?"* — and, after the list: *"it might be kind of nice if these things
were optional modules that you could add in? or should they all be part of
ibex2? maybe if they are small it's better to just include them."*

This document records the list as measured against the crate on 2026-09-03,
decides the packaging shape, and orders the work. Three findings shape it:

- **Both consumers ask for a strict subset of WinterTC.** Exact 2's LLP 1027
  D10, accepted today, wants "the WinterCG minimum minus time and streams" as
  Rust bindings; Snapback 2's effects (LLP 1003 §1) want `fetch`, `console`,
  timers, `URL`, the text codecs, and `randomUUID`. WinterTC is therefore the
  right *ceiling* for the JavaScript tier — it is what npm packages target,
  and LLP 0057 OQ2 says Exact 2 will run npm code — while LLP 0059 §7's rule
  still orders what gets built.
- **"In Rust" is true for about half of WinterTC.** Per LLP 0057 §3.1 Rust
  owns bytes, parsing, state the platform touches, and transport; object
  plumbing — `EventTarget`, `AbortController`, the stream controllers — is
  JavaScript over Rust. §2's table says which, item by item.
- **The Expo-shaped list is the grant-family pattern, not a new mechanism.**
  Five families exist and three are specified. Each platform capability below
  is one more: a parameterized question, a Rust trait, a platform backend, a
  JavaScript binding, a no-engine test. Two pieces of infrastructure come
  before most of them (§4), and the packaging answer (§5) is: *in the crate,
  feature-gated where a family pulls a dependency or a platform framework,
  never a plugin.*

Implementer and date are named per lane when a lane starts (§6). Only what
runs binds; this is a plan.

Everything in that table is either built or specified. What is neither built
nor asked for is the rest of WinterTC and the whole platform layer — which is
what this document is for.

**Streams are the fork.** They are a third of the interface list, the most
expensive item on it (Node's and Deno's implementations are thousands of lines
of JavaScript each), and JavaScript per the split. The first npm package that
reads `response.body` or iterates a body with `for await` hits the exclusion.
Recommendation: keep the exclusion until that package is named — nothing
either consumer runs today needs them, and 0059.000 §5's argument that the
caller-set ceiling, not streaming, is what bounds a body still holds.

## 3. The platform layer, Expo-shaped

pattern. Left out on purpose: view components, Expo UI, Router, Image, Blur,

A family lands in the shape LLP 0069 and LLP 0070 landed in, and nothing

beside the Keychain's on Apple), a Linux implementation, and a memory

## 4. Three things that come first

Each is one design, and each blocks a column of the tables above.

**Events into JavaScript.** `task.rs` delivers two things: settlements and
timers. WebSocket messages, a location watch, a notification, a network
change, an incoming URL — every event-bearing family needs a *subscription*
whose deliveries enter the one sequence-numbered FIFO LLP 0058.000.000 §8
requires, so an application observes one order between a timer, a settlement,
and an event. For the Rust consumer this forces LLP 0068 OQ3: a synchronous
binding cannot deliver an event. Designed once, in lane L3; `WebSocket` is
its first user.

**The OS permission as a second gate.** The manifest grant is the runtime's
authorization. iOS and Android add a prompt and a usage string; macOS adds
TCC. A binding must report *granted by the manifest, refused by the OS* as its
own error, distinct from a denial, so a consumer can prompt rather than
conclude it was never allowed. LLP 0067 §3 gains that sentence with the first
OS-gated family (lane L5), not before.

**The cut LLP 1027 D9 asks for.** `exact-js` links the engine adapter, the
`fetch` binding and its pump, and the pure tier's bindings — never the loader,
ESM lowering, `require`, or timers. Today those are one crate with `hermes`
and `loader` features and one binding installer. That cut is owed to an
accepted RFC and is lane L1.

## 5. Packaging — included, gated, or a crate

Charlie's leaning — *if they are small, include them* — is the answer, with
the number that makes "small" checkable and the one thing that must never be
optional.

**D1 — The families are one closed enum in the core, never a plugin.** The
check is one chokepoint over one grammar (LLP 0067 §3). An open registry of
families is exactly the apparatus Ibex 1 grew around its registry, and a
separate crate cannot add an `Operation` variant without it. The grammar and
the admit for every family live in `grant.rs` and `boundary.rs` whether or not
the family's backend is compiled.

**D2 — What is optional is what a family pulls in.** A family whose Rust is a
few hundred lines and whose backend is a system call is simply in. A family
that pulls a third-party crate or links a platform framework is a cargo
feature on `ibex2`, **default on**, named for the family — `crypto`,
`websocket`, `location` — the shape `hermes` and `loader` already have.
Off, the binding is present and refuses with a named `Unavailable`, the same
way LLP 0068 §1 has a consumer granted nothing hold bindings that refuse
rather than absent ones: `Bindings` keeps its shape and a consumer's code
compiles either way. Exact 2's own rule — an optional capability is a
separate artifact, never a cargo feature on a core crate — is about Exact 2's
crates; `ibex2` is a dependency its hosts already link with
`default-features = false`, and a feature here only ever widens what is
*linked*, never what is *granted*. Feature unification across a workspace
therefore costs bytes, not authority.

**D3 — Backends are traits a consumer substitutes; a separate crate can be a
backend, never a family.** `Transport`, `SecretStore`, and `KvStore` are
already this, through `Host::with_transport` and its siblings. Every family
below gets the same: the trait and the default backend in the crate, and a
consumer with its own — a test, a platform ibex2 does not build for, an
enterprise store — hands one in.

**D4 — The engine is its own crate.** LLP 1027 D9 item 2 proposes
`hermes-lean-sys`: the vanilla lean VM and `hermesc` per platform, the
receipt that binds bytecode to VM, the headers and link lines, shared by
ibex2's engine layer and `exact-js`. That is a cross-repository lane and the
one genuine "separate module" in this plan. It replaces the directory-and-path
in `build.rs`, and it is where the Linux lean build and the iOS device
measurement (LLP 1027 §10 Q7) get done once.

**D5 — "Small" is a number, recorded not remembered.** Every default-on
family is a row in `metrics/ibex2-speed.jsonl`: its stripped size delta on the
run-only binary and its delta at the floor. Proposed, for Charlie to set:
default on at **≤ 150 KB and ≤ 50 µs**; above either, off by default and named
in the consumer's `Cargo.toml`. Diagnostic like the rest of `metrics.mjs`,
never a blocking check — `rules/RULES.md` §Agents forbids adding one without
the human saying so.

## 6. The lanes, in order

Ordered by who is waiting. Each names its scope, its split, what it touches,
and what *done* means. Implementer and date are filled in when a lane starts;
a lane that starts links this document into `llp/current/` if it has been
unlinked.

### L1 — The `exact-js` cut

*Scope.* A consumer links the engine adapter, the `fetch` binding and its
pump, and the pure tier's bindings, without the loader, ESM lowering,
`require`, or timers. And the engine build moves behind `hermes-lean-sys`
(D4), so `build.rs` consumes a crate rather than a path.

*Touches.* `Cargo.toml` — a `timers` feature beside `loader`; `loader` grows
to cover `loader.rs`, `esm.js`, and `require`, which it does not today.
`engine/hermes.rs` — one installer per binding group rather than one
`install_bindings`, so a consumer chooses. `build.rs` — the link lines from
the new crate. `loader.rs` — `ALLOWED_GLOBALS` becomes the union of what the
chosen groups install, asserted the same way.

*Done when.* A binary with `hermes` on and `loader` and `timers` off runs the
pure tier and a grant-checked `fetch` through the adapter, with no `oxc_*`
symbol and no timer global in it; `exact-js` in the exact2 repository links
`ibex2` that way; `node scripts/metrics.mjs` shows the floor unchanged.

### L2 — `crypto`

*Scope.* `crypto.getRandomValues` and `crypto.randomUUID` (0059.000 §3.9),
then `crypto.subtle` at exactly §3.14's algorithm set — digest SHA-256/384/512;
HMAC; ECDSA P-256; Ed25519; AES-GCM; HKDF and PBKDF2; `importKey`/`exportKey`
in `raw`, `pkcs8`, `spki`, `jwk`; `generateKey`. No RSA, no SHA-1, no MD5.
Ungated, as §3.9 argues: computing a digest conveys no authority.

*Split.* All Rust: `stdlib::crypto`, pure, no host needed — the Rust consumer
calls it directly. `CryptoKey` is an opaque handle in the boundary's table;
material crosses only on `exportKey` of an `extractable` key. JavaScript is a
thin `crypto.js`. The CSPRNG is the platform's through the `getrandom` crate.
The algorithm crates are the first D2 decision: RustCrypto's set
(`sha2` is already a dependency; `hmac`, `p256`, `ed25519-dalek`, `aes-gcm`,
`hkdf`, `pbkdf2`) against `ring`, which rustls already links off Apple —
chosen in the lane by the D5 size row, since the API is the same either way.
Feature `crypto`, default on.

*Done when.* The WPT WebCryptoAPI subset for the listed algorithms passes
under the testharness binding; a known-answer vector per algorithm in Rust; a
Snapback effect can call `randomUUID()`; `ALLOWED_GLOBALS` gains `crypto`;
the D5 row is recorded.

### L3 — Events, abort, and the second direction

Three halves that ship together, because the first two are useless without
the third's cancel path and the third is untestable without the first two.

*JavaScript plumbing.* `Event`, `EventTarget`, `CustomEvent`, `ErrorEvent`,
`PromiseRejectionEvent`, `DOMException`, `AbortController`, `AbortSignal`
(with `timeout()` and `any()`), `reportError`, `self`, `navigator.userAgent`,
and `onerror`/`onunhandledrejection`/`onrejectionhandled` wired to Hermes's
promise-rejection tracker. One `events.js`, compiled to bytecode like the
rest. `ALLOWED_GLOBALS` grows by exactly those names.

*Cancellation in Rust.* `Request` gains a cancel token; each transport honours
it — `NSURLSessionTask.cancel` on Apple, a flag checked between reads in the
rustls and dev-TCP transports. An aborted `fetch` rejects with an `AbortError`
`DOMException`, worded once in Rust.

*The subscription.* `HostTask::Event { subscription, payload }` as a third
variant in the one FIFO of `task.rs`; a `Subscription` handle on the Rust
side with one other operation, unsubscribe; the pump delivers into the
callback the binding registered. For the Rust consumer, LLP 0068 OQ3 is
answered here as the smallest thing that works: a `watch` returns a
`std::sync::mpsc::Receiver`, the consumer's loop blocks or polls, and no async
runtime is chosen for anyone.

*Done when.* A test in `task.rs` admits a timer, a settlement, and an event
and observes them in admission order; an in-flight `fetch` aborts observably
on all three transports; the WPT subsets for `AbortSignal`, `EventTarget`,
and `DOMException` pass; a Rust consumer test receives events on a
`Receiver` with no engine linked.

### L4 — `WebSocket`

*Scope.* 0059.000 §3.12 as written: the WHATWG interface, the four events,
`net.websocket` per origin. The first user of L3's subscription.

*The lane's first decision.* §3.12 has Rust own framing, the closing
handshake, ping/pong, and the close-code taxonomy, and the platform own the
socket and TLS — which on Apple means a raw TLS byte stream from
Network.framework, not `NSURLSessionWebSocketTask`, which frames for itself
and brings proxy and VPN traversal with it. The lane measures what the second
loses before overturning the first; either way the transport trait's unit is
decided here and recorded in §3.12.

*Touches.* `stdlib/websocket.rs` (framing, ~500 lines or a vendored protocol
module), a transport method per backend, `websocket.js`, the family in
`grant.rs`/`boundary.rs`, a `Bindings` field. Feature `websocket`, default
on if D5 allows.

*Done when.* An echo over loopback on both transports, plaintext and TLS;
close-code tests; a grant denial for an ungranted origin that never opens a
socket; the D5 row.

### L5 — Platform families with a named consumer

The §3 table, in cost order, and **none before a consumer names it** —
LLP 0059 §7 and LLP 0067 §8 order this lane, they do not schedule it. What
each costs, so the first ask is cheap:

1. **`device.read <name>`** — model, OS and version, app version and build,
   bundle identifier, locale, time zone. The `process.env` shape: a snapshot
   of the granted names, absent rather than refused. Apple: `sysctl`,
   `NSBundle`, `NSLocale`. Linux: `/etc/os-release` and the environment. No
   OS gate. Gated by name (§8 OQ3).
2. **`net.state`** — online, interface type, and a change subscription.
   `NWPathMonitor` on Apple; on Linux, honest `unknown` until a call site
   pays for netlink.
3. **`link.open <origin>` and the incoming-URL subscription** — the
   AuthSession shape. ibex2 owns the grant and the subscription; the host
   owns scheme registration and hands the redirect in.
4. **`clipboard.read` / `clipboard.write`** — `NSPasteboard`/`UIPasteboard`;
   Wayland and X11 are a decision, not a default.
5. **`notify.*` and `location.*`** — the first OS-gated families; the
   LLP 0067 §3 sentence from §4 lands with whichever is first, and the
   binding's error taxonomy gains *refused by the OS*.

Every one ships the §3 checklist whole — the grammar line, the admit, the
trait with three backends, the `Bindings` field, the binding, the no-engine
test, the metrics row, the LLP 0067 row.

### L6 — `Blob`, `File`, `FormData`

With the first multipart or file-upload call site — most plausibly an Exact 2
upload. Rust: a multipart encoder in `stdlib/fetch.rs` and `Blob` bytes as
boundary handles. JavaScript: the three shapes over those handles.
`Blob` was in LLP 0059 Tier I for vendored code only, so this waits.

### Not planned, with the trigger for each

- **Streams** — the first npm package Exact 2 pulls in that reads
  `response.body` or iterates a body. Then `CompressionStream` behind it.
- **`URLPattern`** — a router call site.
- **`MessageChannel`, `Worker`** — a call site; both were removed with one.
- **`WebAssembly`** — the engine's, and vanilla Hermes lacks it. Not ibex2's
  to build; a consumer that needs it needs a different engine build.
- **UI-presenting Expo modules** — host modules through the registry
  (LLP 0059 §4), never standard library.
- **Sensors** — the host's frame clock.
- **Background tasks** — each consumer owns its scheduler.
- **SQLite** — stays the host module it already is (0059.000 §3.15).

## 8. Open questions

**OQ1 — The D5 thresholds.** 150 KB and 50 µs are proposed. Charlie sets
them; `metrics.mjs` records against whatever they are.

**OQ2 — WebSocket's platform unit.** A raw TLS stream with Rust framing, as
§3.12 says, or `NSURLSessionWebSocketTask` with its framing and its free
proxy traversal. L4's first decision, measured.

**OQ3 — Is `device.read` gated?** Proposed yes, by name, because the union of
those facts is a fingerprint and the `env.read` shape makes gating free. The
counter-argument is §3.9's: gating harmless reads trains reflexive granting.
Decide with the first call site.

**OQ4 — Does Snapback 2 want any of L5?** Its effects run headless on a
server; `device.read` and `net.state` are the only plausible asks, and
neither has been named.
