## Overall Assessment

I independently opened the cited ibex sources and confirmed all seven load-bearing code claims are accurate in substance; the RFC's crypto constructions, mint ordering, and revocation linearization are sound; and its residuals are bounded fail-closed rather than hand-waved. The document's single strongest move — replacing a scalar/`handle`-only mint witness with the complete `{policy, negative, dynamic, handle}` tuple per authority source — is not just asserted but proven against the actual generation code and its regression test. ## Material Findings

None. No claim is contradicted by the code, and no unforgeability hole, unclosed TOCTOU, key-reachability route, downgrade/confused-verifier path, or missed-revocation race remains open.

Threat-model stress results against the six sharpest questions:

- **(a) Key facility.** The verified Secure Store surface is generic-password-only with no `kSecClassKey`/sign/verify; the facility uses a Secure Enclave sign-only P-256 key or a separately-entitled HMAC access class, with a hard invariant that no present/future JS module or host call may accept an access-group selector or `kSecClassKey`/application-tag lookup naming facility state (such a route makes HMAC unavailable until re-proven). Forced-fallback/downgrade is closed by the atomic `(algorithm, keyId, class)` pin plus terminal-loss-on-mismatch: a deleted enclave key does not bootstrap an attacker-planted HMAC key ("verify accepts only the facility atomic pin/live-key identity, never message or public-store selection"), and initial HMAC selection requires proof of no enclave AND no prior provisioning. Airtight as designed; residual is implementation-proof of the isolation, honestly gated unavailable.
- **(b) TLV + algorithm rule.** Verify authenticates the exact received bytes of tags 1+2 (never parse-then-re-encode), with `u64_be(length(U))` length-prefix and a domain-separated preimage; unknown/duplicate/out-of-order/non-minimal tags and unknown enums reject before signature acceptance; inner typed values require byte-for-byte JCS re-encode equality. Alg-confusion (alg=none, ES256-pubkey-as-HMAC-key) is closed by out-of-band `(issuer, intendedAudience, kind, keyId)→(algorithm, key)` pinning with `keyId→at most one (algorithm, key, kind, issuer)`. HS256 confined to a single authority domain "because every HMAC verifier is also an issuer" is correctly reasoned; ES256 mandatory cross-domain. Cross-audience replay is closed by singular `intendedAudience` plus mandatory `(issuer, intendedAudience, operationId)` nonce consumption in one protected transaction before any portable execution. No confused-verifier/replay left open.
- **(c) Mint ordering.** Sync capture at JSI entry → four-layer + typed authority before staging → authenticated-handle staging (no raw caller path → confused-deputy closed) → native digest of the exact transport artifact → generation-linearized compare-and-commit under the common guard held from the last read through epoch advance and SQLite commit/rollback. A revocation cannot slip between the typed decision and commit: revocation publications acquire the same guard and advance registry generation before exposing the mutation, so they linearize either before the guarded re-read (caught by equality) or after commit (the lease binds registry generation and is terminally revoked). Sync capture is honestly identified as a required new module-gate hook because the current trampoline captures nothing.
- **(d) Verify + write-once.** Sole-writer is constructed, not assumed: `O_CREAT|O_EXCL` is called out as insufficient and `UF_IMMUTABLE` as same-UID-clearable, requiring atomic seal or fd-unreachability, else unavailable. The digest recheck is explicitly labeled defense-in-depth, not the theorem ("hash-then-open on a mutable file is still check-then-use"). The Apple `fromFile:`-needs-a-named-file tension is an honest, named blocker gated to background-unavailable until a construction is proven. Verify needs nothing from live JS: receipt/lease/registry/epoch are native, and projection recompute uses the native authenticated snapshot (native arming does not require app JS by construction).
- **(e) Freshness epoch + revocation.** The anti-rollback epoch lives outside the rollbackable journal (hardware monotonic counter where available, else named residual + server-idempotency-only mode); "a mutable Keychain item is not automatically a monotonic counter." The JS-dead registry consumes the same authenticated `{policy, negative, dynamic, handle}` generations that the decision cache uses, restores high-water generations before verify, and never republishes zero. The per-install boot salt's value is honestly bounded ("if it restores with the journal it provides no cross-install protection... make no resurrection claim"). GCM-SIV misuse-resistance is correctly treated as defense-in-depth over a real monotonic `sealSequence`, not permission to reuse; plain GCM is rejected as a v1 substitute.
- **(f) Coherence + altitude.** The LLP adds no policy engine or namespace (§1), consumes `to_jcs_bytes`/typed principals/generations/armed snapshot/WP6 as inputs, and does not re-own 0021 transport or 0013 policy (§10). It covers each obligation 0476 §16 delegates and contradicts nothing in 0476 §14/§16: both hold armed background closed until WP6, both defer the portable capsule kind, both require ES256 cross-domain / HS256 single-domain, both make inbox/journal mandatory protected objects, and both use a native-held receipt for the first consumer. Where 0052 changes 0476's certificate shorthand (`armedSnapshotDigest`→`durableAuthorityProjectionDigest`; `{sourceId, grantId}`→tagged provenance), 0476 §2 explicitly delegates the byte-exact schema here and expects the mechanical update — this is the delegation working, not a conflict, and the projection-digest substitution is a genuine improvement (authority survives benign restart; raw `armedSnapshotDigest` would not).

## Minor Findings and Nits

1. **Code-citation line anchors drift by a few lines** in several places (e.g. `capability.rs:705-728`→fn at `:710`; `mod.rs:4149-4168`→fn at `:4129`; `mint_typed_handle` handle-generation advance is at `:4374`). Substance is correct and the ibex convention treats line numbers as anchors; worth a light refresh when convenient but not blocking.
2. **The `insecure` build feature bypasses the armed hard-deny.** `Host::check_handle_mint` returns `true` under `cfg!(feature = "insecure")` (`host/mod.rs:4643`), and `Cargo.toml:205` defines `insecure = ["unadvertised-dev-arming"]` (LLP 0038 dev-only, unshipped). This is orthogonal to the RFC, but §8 conformance should positively assert the durable facility is compiled out / reports unavailable under `feature = "insecure"`, so a dev build can never present a durable signing oracle.
3. **`channelEpoch` exclusion rests on a classification the conformance must positively assert.** §3 excludes exactly `armedSnapshotDigest`, `runNonce`, `channelEpoch`. The projection's soundness depends on the exclusion set being precisely the non-authority-bearing fields; §8 should include a positive assertion that `channelEpoch` (like `runNonce`) carries no authority-relevant state, not only that unknown fields fail closed.

## Answers to the Standard Questions

- **Good idea?** Yes. A durable, JS-dead-verifiable authority that JS can neither hold nor author is the correct primitive for background native work, and grounding it as an explicit extension of the `ArmedSessionToken`/`mint_typed_handle` precedent (rather than a new trust root) is the right architecture.
- **Good plan?** Yes. Every capability is gated behind a named platform proof (§2/§5/§6/§7) with fail-closed unavailability, the certificate/envelope/AEAD/generation bytes are frozen, and conformance (§8) enumerates the adversarial cases (downgrade, planted-HMAC, TLV malformation, nonce-uniqueness through crash/rotation, write-once descriptor attacks, external revoke before/after observation, JS-dead recovery).
- **Add / remove / change?** Add the three §8 assertions in Minor Findings (insecure-build exclusion; positive `channelEpoch` classification; and, per Novel Ideas, a mechanical full-key-set equality check). Nothing to remove.
- **Definitely / possibly wrongheaded?** Nothing definitely wrongheaded. The one thing I scrutinized hardest — carrying the global generation tuple on every authority-source item, accepting that unrelated authority mutation may invalidate a lease — is an explicitly-chosen fail-closed availability cost, correctly labeled, with per-source clocks deferred to a later schema. That is the safe direction.
- **Novel ideas?** See below.
- **Key open questions?** The five §11 questions (Apple write-once mechanism; atomic key+pin + monotonic-epoch-across-restore; first portable kind's issuer/audience/rotation protocol; whether a background adapter can meet WP6; and typed private-inbox representation) are the right ones, each with a fail-closed default. All are implementation-selection, not design gaps.

## Novel Ideas

1. **Make the projection's forward-safety a single mechanical equality.** Have arming emit a canonical sorted key-set digest of the full armed-snapshot top-level object; the durable facility then asserts `(classifiedFields ∪ excludedFields) == actualTopLevelKeySet` before minting. This turns "any new/unclassified field ⇒ unavailable" from a prose obligation into one equality the conformance suite checks directly, closing the risk that a future snapshot field silently rides through an out-of-date manual enumeration.
2. **Cross-bind the epoch anchor into the AEAD record.** Fold the anchor's current high-water generation into the `nativeSealedRecord` AAD (alongside `installationBinding`) so that a rolled-back-anchor + otherwise-valid-record combination is self-inconsistent at open time — an authentication failure rather than only a separate epoch-behind refusal. Belt over the §5 `sealSequence` suspenders.
3. **Machine-declare the class-1-only availability subset.** Since class-2 (view-broker) durable authority is gated until the broker binding lands, register the class-1-eligible capability/target pairs as an explicit machine-readable subset (per LLP 0292 honest-reporting) rather than prose, so the honest availability surface is queryable and the view-broker gap can't be accidentally overstepped as the broker owner is wired.

## Implementation-Phase Notes

- **Verify's projection recompute in a JS-dead background relaunch** presumes native re-arming (snapshot load + authenticate) is available without app JS. This is true by construction (arming is native Rust), but the implementation should confirm the background-resume path actually re-authenticates the snapshot before verify recomputes the projection, and state it explicitly.
- **Sync authority-context capture hook** (§1/§4/§7) is a new module-gate contract the current trampoline does not provide; its callback-affinity registration and LLP 0297 async-first compatibility should be landed and tested with the Promise/queue/`setTimeout(0)` hop cases (0476 §15.1).
- **Field-classification conformance** (§8) should include the positive `channelEpoch`/`runNonce` no-authority assertion and the insecure-build exclusion noted above.
- **Platform proofs (§2/§5/§6/§7)** remain the gating work: atomic key+pin provisioning and isolation, fd-unreachable/atomic-seal write-once through every URLSession reopen, the monotonic epoch anchor across restore, and a WP6-meeting background adapter. Each is honestly gated to unavailable until proven, which is the correct posture, not a blocker at RFC altitude.
