The remaining implementation findings are:
1. **MATERIAL — `cycle()` does not report and resume a throwing microtask checkpoint.**
   Both drains are direct, unprotected calls at [install.cc:2335](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/install.cc:2335) and [install.cc:2338](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/install.cc:2338). The governing contract requires reporting the escaped job error and resuming behind that job: [LLP 0058.000.000:533](/Users/ccheever/projects/ibex2-0071-impl/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:533). The owning pump implements that loop at [hermes_shim.cc:259](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2-runtime/src/engine/hermes_shim.cc:259).
   The exact consequences are:
   - A **pre-checkpoint throw** exits before timer admission or host-task take. Existing host tasks remain queued; remaining microtasks are not drained.
   - A **post-checkpoint throw** exits after the host task was consumed. An interval has already been rescheduled. That task is not rolled back; remaining microtasks and subsequent host tasks remain pending.
   - In both cases, `DriveRelease` correctly clears the flag during C++ unwinding. This is **not a leaked-flag bug**.
   - No `Cycle` result is returned, and the adapter does not report the exception through its error path. Another `cycle()` can resume through its pre-checkpoint, but recovery has become the caller’s responsibility.
   The fixture catches the exception and returns `-1`, which its Rust wrapper turns into a failed assertion: [embedding.cc:331](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2-runtime/tests/embedding.cc:331), [embedding.rs:389](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2-runtime/tests/embedding.rs:389).
   Add a borrowed checkpoint helper with reporting/resumption and tests that actually make `drainMicrotasks()` throw. An ordinary throwing Promise reaction will not establish this: Promise machinery catches that exception.
2. **MATERIAL — Detaching during a cycle can dereference a null runtime.**
   `cycle()` checks `alive` only upon entry. A native function reached from a timer callback can call `Adapter::detach()` while leaving the adapter, Context and engine objects alive. Detach sets `runtime_ = nullptr` at [install.cc:569](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/install.cc:569); returning from the callback then reaches the unconditional post-checkpoint at [install.cc:2338](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/install.cc:2338).
   Detach during the pre-checkpoint has the same missing revalidation. This is consistent with an owner-thread call under the public header’s stated threading restriction, and the lifecycle specification expressly allows Closing during project JavaScript while prohibiting a subsequent checkpoint: [ibex2_jsi.h:247](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/include/ibex2_jsi.h:247), [LLP 0058.000.000:587](/Users/ccheever/projects/ibex2-0071-impl/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:587).
   Revalidate lifecycle after each JavaScript entrance. Also address the guard’s lifetime: it retains only a borrowed raw queue pointer at [install.cc:2313](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/install.cc:2313), so releasing the Context after reentrant detach must not invalidate that pointer before guard destruction.
3. **MATERIAL — The interval run count eventually overflows.**
   `runs` is `u32`, and admission increments it with unchecked `entry.runs + 1`: [timers.rs:55](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/stdlib/timers.rs:55), [timers.rs:167](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/stdlib/timers.rs:167).
   After `u32::MAX` delivered occurrences, checked-overflow builds panic during admission; admission is called through a non-unwinding C ABI. Ordinary release builds wrap to zero and temporarily remove the 4 ms clamp. Caller-controlled time makes elapsed wall time an inadequate bound on this counter.
   Saturate the counter—only whether it has reached five matters—and test that transition directly without executing billions of callbacks.
4. **MATERIAL, pre-existing — Large finite timer delays can still abort the process.**
   JavaScript rejects non-finite and negative delays but accepts `1e300`: [timers.js:34](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/timers.js:34). `set_timer` then calls the panicking `Duration::from_secs_f64` conversion at [task.rs:1076](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/task.rs:1076), reached through [boundary_abi.rs:325](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/boundary_abi.rs:325).
   Thus `setTimeout(function () {}, 1e300)` can panic across `ibex2_host_call`; the clock callback’s `catch_unwind` does not protect this conversion. Separately, casting a sufficiently large valid `Duration::as_micros()` to `u64` truncates before the saturating deadline addition: [timers.rs:123](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/stdlib/timers.rs:123).
   These defects existed before this commit; they are not regressions introduced by r3. They remain reachable through the audited timer surface.
The requested clock and synchronization checks otherwise look correct under the documented owner-thread rules:
- **Source selection and sealing:** `OnceLock::set` and `get_or_init` arbitrate one immutable source. The callback executes after initialization has finished, so initialization synchronization is not held during it. A concurrent first read cannot publish an Instant sample after successfully switching to a caller clock: [task.rs:1040](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/task.rs:1040).
- **Atomic maximum:** `fetch_max(sample).max(sample)` returns the maximum at that operation’s linearization point; invalid readings load the existing maximum, initialized to zero. NaN, infinities, negative values and values above the bound fail the range check. The accepted bound multiplied by 1,000 fits `u64`: [task.rs:1050](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/task.rs:1050).
- **Locks and FFI:** scheduling, admission and deadline queries sample before locking the wheel. Timer take releases both the FIFO lock, by returning from `queue.take()`, and the subscription guard before sampling. Non-timer takes do not sample. Ordinary unwinding clock panics are caught inside Rust before returning through either host-call or task-take FFI.
- **Drive ownership:** on ordinary returns and C++ exception unwinding, acquired guards release exactly once. Detached and nested early returns construct no guard; rejected `deliver_one()` calls therefore cannot clear an outer drive flag. Error reporting remains inside the outer guard.
- **Owning-pump interlock:** the new adapter ABI and existing owning ABI both call the same `RuntimeState::begin_drive/end_drive`: [boundary_abi.rs:1273](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/boundary_abi.rs:1273), [loader_state.rs:195](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2-runtime/src/loader_state.rs:195). The owning pump directly takes and dispatches tasks, so it does not double-acquire the adapter guard. The new symbols live in `ibex2`, preserving the engine-independent boundary.
- **Intervals and cancellation:** admission removes an interval from the wheel; take removes its queued record and schedules from the take-time sample. Clearing removes both scheduled and queued records. A cleared admitted occurrence reaches the JavaScript callback-map lookup as a no-op: [timers.rs:142](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/stdlib/timers.rs:142), [timers.js:58](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/timers.js:58).
- **Performance and owning behavior:** strict-mode assignment rejects ordinary non-writable `performance.now` properties. Timers install before events, which capture the installed function: [bindings.rs:347](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings.rs:347), [events.js:30](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings/events.js:30). Owning runtimes also gain microsecond quantization, take-time interval rescheduling and the repeat clamp. Their pump ordering and real-time execution deadlines remain unchanged. Adoption copies endowments, not the source Context’s clock: [bindings.rs:655](/Users/ccheever/projects/ibex2-0071-impl/crates/ibex2/src/bindings.rs:655).
