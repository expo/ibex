That is compatible with LLP 0057’s boundary inversion and with LLP 0058’s “engine is not the security kernel.” D1–D6, §3.3’s no-silent-downgrade rule, and the fail-closed posture split in §7 are directionally sound.

The stated security claim can hold **only if every identity-bearing host operation is module-bound** and **every unpatched identity fallback is treated as a defect**. This revision does not actually decide those points. Production evidence in the capsule still installs identity-bearing APIs on the real global and documents that an unpatched engine **keeps linking** through a thread-local principal. ## Findings

1. **Identity-bearing host ops (timers especially) are not under D4, but they cannot be per-module on `globalThis` without stack provenance.**  
   D4’s load-bearing example is `fetch`. D2/D6/M2 nonetheless treat timers as enforcement-relevant: Rust owns timer identity, a timer retains the bound operation’s context, and the live adapter still calls `currentPrincipalId()` / `exactCollectTypedPrincipalStack()` from `setTimeout` / `clearTimeout` / ref-unref installed on the real global (`src/engine/hermes_runtime_timers.cc`).    **Disposition:** State the rule once: every operation that today reads engine identity is capability-bearing for D4 (module-bound; absent from the shared real global in the per-module secure profile). Anything that remains on `globalThis` must not read caller identity and must not confer grants.

2. **The documented unpatched principal fallback is not named as a forbidden class.**

Patch 0007 exists because principal `0` on an empty stack was trusted root; vanilla Hermes will not carry 0007. M2 only requires listed Ibex 2 ops to stop calling `currentPrincipalId()`. 8.1 only forbids *requiring* patch-only symbols. Neither forbids a stub that returns thread-local/`0` when provenance is absent.

### MATERIAL — Job-queue contract is still open, while the child RFC cites it as if it existed
**Targets:** LLP 0058.000, LLP 0058.000.000

LLP 0058 §3 requires a **stated** job-queue contract; §5 OQ1 still asks the gating question (ordering of host-completed futures vs engine-enqueued jobs) and says it must be answered before a second engine. LLP 0058.000 §4.5 then requires adapters to interleave “per LLP 0058's job queue contract.” That contract is not in LLP 0058.

The Spec’s §8 loop (at most one Rust host task, then a Hermes microtask checkpoint) is necessary and is the right shape, but it is not sufficient for independent implementations:

- **Already-queued engine jobs vs native completions.** §8 starts at “ask Rust for one ready task.” It does not require draining Hermes jobs that are already queued **before** that host task. An adapter that pumps a ready `fs.readFile` settlement ahead of an already-queued `queueMicrotask` / Promise reaction reorders relative to LLP 0058 §3’s rule that an off-thread Rust completion “must not reorder relative to JavaScript-enqueued jobs.”
- **Fairness among host-task classes.** Timer due-work and async completion settlement are both “host tasks,” with no admission order when both are ready.
- **Nested drives.** LLP 0040 restores the prior engine/carrier on nested drive unwind. The Spec never forbids a host callback from re-entering the Rust pump before the outer checkpoint, which would skip §8.6.
- **Teardown vs the engine queue.** §9 drops **Rust** owner tasks without JS. It does not say whether Hermes jobs already in `jobQueue_` still run after `Closing`. Those jobs can still invoke bound callables.

**Disposition:** In LLP 0058.000 §4, replace the citation of LLP 0058’s contract with a reference to Spec §8, or stop claiming the parent already answered OQ1. In Spec §8, add the outer drive: (1) no nested Rust pump; (2) drain already-queued Hermes microtasks before taking a newly ready host completion; (3) one FIFO of admitted host tasks (timers and completions); (4) `Closing` prevents further **engine** job execution visible to project code, not only the Rust queue. Close LLP 0058 OQ1 by pointer once that text exists.
