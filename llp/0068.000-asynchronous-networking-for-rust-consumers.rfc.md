# LLP 0068.000: Asynchronous networking for Rust consumers

**Type:** RFC
**Status:** Accepted
**Systems:** Rust Stdlib, HTTP Transport, Host ABI, CapSec
**Author:** Codex for Charlie Cheever
**Date:** 2026-10-13
**Accepted:** Charlie Cheever, 2026-10-13, by directing implementation of these three documents.
**Revised:** 2026-10-13 (one Astra Max and Grok 4.7 xhigh approach review; admission and deadline boundaries clarified)
**Implementer:** Codex under Charlie Cheever's 2026-10-13 commission; implementation authorized by Charlie Cheever and sequenced by LLP 0068.002.
**Related:** LLP 0068 §2 (blocking Rust primitives), LLP 0057 §3 (Rust semantics and platform mechanism), LLP 0059.000 §3.5 (fetch), LLP 0067 §3 (grant admission), LLP 0068.002 (consumer patch adoption); Exact sources pinned in §1.

## Summary

Add an engine-free, executor-neutral asynchronous HTTP interface alongside
the blocking Rust fetch interface. Reuse Exact's callback transport and fetch
state machine, sharing the existing redirect and grant rules. A consumer owns
admission, scheduling, whole-request deadlines, and resource budgets. Ibex
owns protocol semantics, per-request limits, transport lifetime, and precise
notifications that let the consumer account for resources.

This proposes a narrow amendment to LLP 0068 §2: HTTP need not occupy a worker
while the platform waits for the network. Ibex still chooses no Rust async
runtime, reactor, application executor, or scheduling policy. The first
surface collects a bounded response. Existing demand-driven blocking
`Fetch::stream` remains the streaming path until asynchronous body demand has
its own qualified contract.

## 1. Evidence and current state

Upstream `Fetch::stream` blocks for headers and returns a pull-based body;
`send` and `get` collect that path. Abort interrupts native work, and every
redirect checks the destination grant. Upstream does not currently expose
Exact's asynchronous HTTP interface.

The reusable boundary is the exchange and fetch machinery. Exact's ordered
and independent lanes, queue policy, numeric concurrency limits, forgotten
write policy, and performance rollout gates belong to Exact.

## 2. The proposed boundary

Keep the useful division from the prototype:

| Element | Responsibility |
| --- | --- |
| `AsyncTransport` | Prepare one HTTP exchange; never follow redirects itself. |
| `Exchange` | Explicit activation and idempotent cancellation, separated so the caller can record ownership before delivery. |
| `Sink` | Receive one head, ordered borrowed body chunks, one physical end, and optional connection metrics. |
| `FetchTask` | Apply admission and redirect semantics; enforce limits; choose exactly one terminal outcome. |
| `Upload` | Share one immutable owned buffer between redirect hops and the platform; notify its last release. |
| Consumer | Reserve capacity, start admitted work, schedule subsequent hops, publish outcomes, release charges, and drive deadlines. |

The public binding must retain its endowment's `Arc<GrantSet>` for the whole
fetch. A low-level transport is trusted mechanism, not authority: giving it
a URL never bypasses `FetchTask`'s per-hop admission. No JavaScript runtime
or JSI handle crosses this boundary.

Use the same Rust helpers in blocking and asynchronous paths for request-body
preparation, request-header guards, redirect decisions, redirect limits, and
grant errors. Preserve method/body rewriting, sensitive-header removal on
cross-origin redirects, manual/error modes, and `DeniedRedirect` diagnostics.
The implementation must extract or reuse helpers, not maintain two semantic
copies. API spelling can be settled during implementation; these ownership
and delivery rules are the proposed contract.

## 3. Ownership, callbacks, and cancellation

A prepared exchange has reserved its required execution capacity and sends
nothing before activation. Activation consumes that reservation; it cannot
turn an accepted exchange back into an admission refusal. The caller records its
identity and resources and becomes ready for delivery before invoking
activation outside its state lock. Every accepted exchange reports physical
retirement exactly once, including transport failure and cancellation before
activation; a pre-activation cancellation sends no request. Rejected admission
creates no accepted exchange and produces no transport callbacks.

Transport callbacks are serialized per exchange and never invoked inline on
the initiating stack by `start` or activation. Once activation is invoked,
callbacks on another execution context may race its return; there is no
implicit handshake that waits for the caller to return. Callback work must
be bounded: no waiting for queue space, network
I/O, or consumer scheduling. Chunks are borrowed for the callback only.
Neither Ibex nor the consumer may invoke external callbacks or release
potentially reentrant owned values under their state locks. Panics must not
unwind across the native FFI boundary; implementation must define containment
and ensure terminal cleanup before exposing a platform adapter.

Fetch-level preflight or abort may finish synchronously on the initiating
thread; `FetchEvents` consumers must therefore be thread-safe and tolerate
reentrancy. They may enqueue onto their own dispatcher. Events from different
hops, cancellation, and late metrics can overlap; per-exchange serialization
does not promise a single thread for the whole fetch.

There is one terminal outcome. A stop, deadline, abort, and successful end
compete through the same terminal transition. Late data cannot change it or
start a redirect. An outcome reporting cancellation means no more result
delivery, not that native cleanup or remote side effects have finished.
Hop identity suppresses stale callbacks. A next-hop continuation must recheck
terminal state and authority when actually run, even if it was queued before
the abort. The consumer must eventually run or discard queued continuations
and release their captures during retirement.

Keep three distinct lifetime signals: terminal outcome, each hop's physical
end, and final upload-buffer release. The consumer retains an in-flight
permit until physical end and upload charges until all outstanding holders
release them. Publishing or discarding an outcome alone cannot refund those
resources. Metrics may arrive after physical end and must not keep upload
bytes or running permits charged; their retained metadata must be bounded.
Dropping a control handle is not an implicit rollback. Retirement explicitly
aborts outstanding fetches, prevents new starts, and allows native cleanup
to finish without dereferencing retired consumer state.

## 4. Limits, flow, and deadlines

The initial asynchronous binding requires finite response-body and per-hop
header limits. Enforce body limits incrementally, including unknown lengths;
reject impossible declared lengths before accepting the body. Check headers
on intermediate redirects as well as the final response. This extends
Exact's previous final-response header check and needs explicit parity tests.
Native header/chunk allocations precede some Rust checks: document and test
their bounds separately rather than treating a Rust cap as a total process
memory guarantee.

The prototype's `Flow::{Continue, Stop, Skip}` is stop control, not a
pause/resume protocol. A followed redirect skips its body, ends that hop, and
asks the consumer to schedule the next hop. The first supported async fetch
collects directly within its reserved ceiling; it must not insert an
unbounded channel between transport and collector. Multiple requests are
bounded by consumer admission plus each request's ceiling. Consumer outcomes
and retained closures also require consumer-owned bounds.

Do not advertise this interface as asynchronous streaming. Adding that
surface requires byte-credit or equivalent demand, bounded platform buffering,
pause/resume races, and cancellation while paused to be specified and tested.
The existing pull API retains its present semantics during this work.

The consumer arms a real monotonic whole-request deadline at the first
accepted exchange's activation, after initial upload sizing and capacity
parking. Those earlier phases may have their own consumer timer; they do not
start this network deadline. Once armed, that deadline covers all
redirect hops, platform queueing after activation, response consumption, and
any waits between hops; redirects do not reset it. Expiration triggers the
same terminal/cancellation path even if no hop is currently active. A
transport idle/request timeout remains a separate backstop and cannot stand
in for the whole-request deadline. Application virtual time does not extend
the life of native network work.

Ibex requires no timer service: a consumer can drive an `AbortSignal` from its
existing monotonic timer and retain its own typed timeout cause. Tests must
prove that deadline and abort error projection is stable under races. Exact's
upload sizing/parking phases remain its own scheduling contract; a later park
must not reset an already-running network deadline. Tests pin this arm point,
including an upload that parks before the first activation.

## 5. Platform adapters and compatibility

Apple sessions are reusable, lazily created, and explicitly owned by the
consumer's chosen transport scope. The consumer can choose separate sessions
for scheduling domains. Keep cookies and URL cache disabled and native
redirect following off. Connection reuse, protocol negotiation, TLS, proxies,
and trust remain platform work. A session's connection limit is not proof
that the OS never queues; such queueing consumes the armed deadline.

Keep `Transport::open` and the blocking fetch surface. `BlockingAdapter`
permits reuse on other platforms through a consumer-provided bounded worker
service. It is not evidence of thread-free I/O and must not create an
unbounded thread per exchange. A cancelled blocking resolver may retain its
worker until physical return; the consumer must account for that straggler.

Resolve the prototype's admission inconsistency before publishing the API:
`BlockingAdapter` currently reports a rejected spawn inline, although the
transport documentation forbids inline callbacks. A bounded worker adapter
must reserve execution capacity during preparation, before returning an
accepted exchange; refusal is an
explicit synchronous admission error, with no accepted exchange and no
transport callbacks. Once accepted, it follows the ordinary asynchronous
retirement contract, including cancellation before activation. Admission error
handling occurs outside locks and settles the fetch once. No fallback thread
may be spawned merely to hide a rejected worker admission.

## 6. First implementation slice and adoption evidence

The first slice upstreams shared fetch helpers, the bounded collected-fetch
state machine, transport traits, and fake-transport tests. It resolves the
callback/admission inconsistency and proves lifetime rules before adding the
Apple adapter. Keep it opt-in; updating this Draft does not assert that code
exists or that Exact's switch may default on.

Required evidence for that slice:

1. Blocking/async parity on grant denial at a redirect, method/header changes,
   manual/error modes, malformed redirects, body ceilings, and abort.
2. Deterministic races: abort before activation, between hops, during body
   delivery, after outcome, and during retirement; end before/after upload
   release; stale metrics; worker refusal; reentrant callbacks. Counters show
   one outcome and one physical end per accepted exchange, with no leak.
   Include callback delivery overlapping activation's return, and cancellation
   of a prepared exchange that is never activated.
3. Engine-free build and focused Rust tests, workspace clippy, and ref-check.

Then qualify Apple's reusable session with local HTTP fixtures, connection
metrics, capped concurrent requests, bounded retained bytes, and repeated
transport teardown. Demonstrate connection reuse and compare throughput,
latency, memory, and thread counts against the current blocking path. A
bounded non-Apple adapter gets its own qualification; Apple results do not
qualify it.

The first consumer proof updates Exact to the upstream APIs and removes the
corresponding vendor patch. Run concurrent Exact data requests while Snapback
4 synchronizes queued writes, interrupt connectivity, cancel a media transfer,
and replace the executor/account. Verify successful retry through consumer
policy, no duplicate terminal delivery, no retired-account callback, and
return of network/buffer charges after cleanup. Record the Exact and Snapback
revisions and any unavailable device scenario. Existing Exact stage-1 blockers
remain release blockers for its switch; upstream extraction cannot waive them.

## 7. Follow-up decisions

The implementation may refine type names and error wrappers without another
design round. Expanding to asynchronous streaming or uploads produced on
demand needs explicit demand and retention semantics first. Whether a native
non-Apple asynchronous transport beats the bounded blocking adapter is a
measurement question, including binary size and dependency cost.

## 8. Implementation record — 2026-10-13

The engine-free surface is implemented in `stdlib::fetch_async`:
`FetchTask`, `AsyncTransport`, `Exchange`, `Sink`, `FetchEvents`, `Upload`,
`HeaderCaps`, and `BlockingAdapter`. `host::Fetch::start_async` retains its
binding's grant set. Blocking and asynchronous fetch use the same
`prepare_body`, `admit_hop`, and `redirect_step` helpers. A denied redirect
carries its destination origin in `HostError::DeniedRedirect`.

`AsyncTransport::start` returns `Result<Exchange, HostError>` and reserves
capacity before `Ok`. The portable adapter accepts `Arc<dyn WorkerService>`;
`reserve` returns a `ReservedWorker`, whose `dispatch` must accept the job and
must not invoke it inline. The provided `BoundedWorkerPool` has a fixed thread
count and a separate finite pending capacity: its upper bound is pending
capacity plus worker count, including prepared but unactivated exchanges.
Queue reservations release when execution starts, allowing a one-worker,
one-pending-slot service to prepare the next redirect from its end callback.
The consumer still owns overall request admission. Blocking DNS may outlive
cancellation and continues to occupy its worker until it returns.

`Exchange::cancel` is idempotent and schedules retirement of a prepared
exchange without requiring the caller to activate it. Outcomes are decided
under the task lock, then notifications and owned resource destruction occur
outside it. Repeated end notifications are ignored. At physical end, the hop
sink releases its strong task reference; late metrics retain only their
observer and hop URL. Panics from outcome/retirement/metrics/release callbacks
are contained so cleanup continues. A panicking next-hop callback settles a
still-pending fetch as failed. Native sink callbacks cannot unwind over FFI;
a panic stops delivery and the adapter still attempts one physical end.

`Request::timeout` is the platform attempt backstop, copied to each hop.
Portable HTTP applies it to the attempt and its phases; Apple's native request
uses its idle timeout. The whole-request deadline is still driven by the
consumer's real monotonic abort signal, armed at first accepted activation and
never restarted by a redirect. No timer or application executor was added.

The asynchronous collector rejects allocation-limit sentinels larger than
`isize::MAX`, enforces the finite body ceiling incrementally, uses fallible
exact reservation, and checks header bytes/count on every hop. Apple bounds
its additional serialized header copy to 1 MiB and 4096 entries before
appending and bounds the copied connection-metrics fields. Foundation already
owns its parsed header dictionary and incoming `NSData` before these checks;
these limits therefore do not claim a total native allocation bound. The
platform callback borrows body bytes directly and inserts no channel or
retained chunk queue. Foundation metrics normally precede completion; optional
metrics arriving afterward are discarded so a grace-period timer cannot keep
consumer closures or uploads alive.

The portable blocking adapter currently makes one temporary upload copy for
`Request::body`; consumers must budget a second upload-sized buffer per running
worker. `Upload`'s final-release notification describes the shared original;
the temporary copy is released before the worker's physical-end callback.
Apple holds one immutable upload owner and supplies replayable private
`NSInputStream` instances through the native
[`needNewBodyStream` protocol](https://developer.apple.com/documentation/foundation/urlsessiontaskdelegate/urlsession(_:task:neednewbodystream:)).
Each read copies at most 64 KiB into Foundation's buffer; `getBuffer` returns
false, so no borrowed pointer escapes. Physical completion detaches the owner
under the same lock as reads and releases its Rust reference after unlocking.
Cached stream metadata therefore cannot retain upload bytes. This replaces
the prototype's `NSData` body after the real upload-release test found that
Foundation retained those bytes beyond completion even with task/session
handles dropped. No extra full-size copy or arbitrary release delay is used.

`portable-http` explicitly exposes `RustlsHttpTransport` on Apple while keeping
`DarwinTransport` as the default and the portable dependency graph absent from
a normal Apple build. `DarwinLane` is the compatibility name for an explicitly
owned reusable native session; it encodes no application lane policy. Session
retirement cancels suspended accepted exchanges as well as activated ones.

Focused evidence lives beside the implementation: shared blocking/async
redirect fixtures; denial-before-network; intermediate header caps; upload
release reentrancy; cancellation between hops; activation-return overlap;
worker admission refusal and preactivation retirement; physical-end and late
metrics separation; native local HTTP, connection reuse, concurrent exchanges,
request timeout, cancellation and panic cleanup. Final verification and the
consumer/device qualification are recorded in LLP 0068.002; this record alone
does not qualify production throughput, memory, or unavailable device targets.

Local macOS verification for this slice: engine-free `cargo test -p ibex2
--no-default-features --lib --no-fail-fast -j2 fetch -- --test-threads=2`
passed 63 tests. The corresponding `transport` selection passed 52 tests
with one existing measurement ignored; this includes real native upload
release while the session and control remain alive, connection reuse, and
both native and portable attempt-timeout witnesses. The upload fixture first
failed against the prototype mechanism and passed after the stream-owner fix.
`./ref-check` passed (25 documents, 200 references). Integrated clippy and
consumer results belong to the coordinated adoption record.

Follow-up native witnesses cover a 256 KiB + 7-byte POST replayed across a
307 and cancellation of an 8 MiB upload while its peer stops reading; both
release the shared buffer while task/session handles remain live. All five
upload-selected tests and all 34 asynchronous state-machine tests passed.
Collector capacity grows geometrically within the finite body ceiling using
fallible exact reservations, avoiding quadratic copying on small chunks.

`host::Fetch::blocking_adapter(workers)` wraps the binding's selected blocking
transport in the bounded service. Exact can pass this adapter to the same
binding's `start_async`, preserving endowed admission without extracting its
private grants or raw transport.
The owning-runtime and primitive-fetch redirect witnesses assert the new
destination-origin diagnostic as well as absence of traffic to the denied hop.

The ignored `compare_native_and_blocking_transport` diagnostic runs each
backend in a fresh subprocess. Its identical local HTTP/1.1 fixture sends
24 responses of 65,536 bytes, each delayed 30 ms, with four blocking workers
or an async session's four-connection limit. It includes cold session setup;
responses close their connections, so the separate persistent-connection test
is the reuse proof. Completion percentiles measure batch submission to
completion, including queueing. RSS and thread samples include the test harness
and the identical server fixture; they are sampled process peaks, not a native
buffer-accounting guarantee.

Command: `cargo test -p ibex2 --no-default-features --lib -j2
compare_native_and_blocking_transport -- --ignored --nocapture --test-threads=1`.
One local Darwin 27.0.0 arm64 run (load averages 250.71 / 266.17 / 295.59
immediately afterward) recorded:

| --- | --- | --- | --- | --- | --- |
| Blocking native | 291.46 ms | 82.35 | 216.01 / 289.48 ms | 7,421,952 / 21,889,024 bytes | 2 / 17 |
| Async native | 285.84 ms | 83.96 | 201.41 / 278.40 ms | 7,421,952 / 22,462,464 bytes | 2 / 12 |

The run demonstrates the expected reduction in blocked application threads,
with similar elapsed time and slightly higher sampled RSS in this fixture.
Its single heavily loaded run does not establish a throughput improvement,

adding a blocking performance gate.
