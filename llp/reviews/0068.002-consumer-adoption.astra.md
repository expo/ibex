- **0068.000 — READY WITH IMPLEMENTATION NOTES**
  Frozen SHA-256: `cbd263ed8a73d92580b5269dd591941147edc3f7f6cf2d8b6f2dab38eea0dd3a`

  The separation of terminal outcome, physical retirement, and upload release is sound. Restricting the first surface to bounded collection also avoids promising streaming without a demand protocol.

  Clarify the admission boundary when defining the API (§§3, 5). The simplest consistent interpretation is that preparation reserves worker capacity before returning an accepted `Exchange`; activation starts that reservation and cannot subsequently reject it as though no exchange existed. An already accepted exchange must retain its retirement obligation even if activation never happens. The current phrase “before accepting activation” could otherwise lead to conflicting rejection paths. This is an implementation contract clarification, not a reason to change the two-phase approach.

- **0068.001 — READY WITH IMPLEMENTATION NOTES**
  Frozen SHA-256: `dec47333fcc3abb8aac35c09669e1406d7285112e000bc2b16317224c8d6ac0a`

  The immediate `CommitStarted` cancellation result resolves the dangerous ambiguity between abandoning delivery and preventing publication. Keeping codec execution and stalled workers charged after cancellation is appropriate.

  Specify selected-file identity precisely (§3). A retained parent handle plus a leaf name identifies a **name within that directory**, not the originally selected inode. Replacing that leaf can therefore change the object later read, even though replacing an ancestor pathname cannot redirect the parent handle. This appears consistent with the proposed atomic-save behavior. Narrow the statement about “moving/replacing the original pathname” accordingly and establish the expected leaf-replacement behavior before porting the provider. If immutable file-object identity is intended instead, the lease design would need reconsideration.

  Ensure the work-count limit also covers settled results awaiting collection (§§4–5). A bound covering only queued and executing workers would allow completed payloads or retained outcome records to accumulate. The existing allocation-accounting requirement supports the right implementation; make ownership of these completion slots explicit.
