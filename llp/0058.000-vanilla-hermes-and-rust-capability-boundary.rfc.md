# LLP 0058.000: Vanilla Hermes and the Rust Capability Boundary

**Type:** RFC
**Status:** Review
**Systems:** Engine, Runtime, Host ABI, Module Loader, CapSec, Build, Security, Conformance
**Author:** Charlie Cheever / Codex
**Date:** 2026-08-27
**Revised:** 2026-08-27 (LLP 0058.000.001 replaces in-place migration with a bounded greenfield kernel; super-refine round 1 earlier the same day)
**Related:** LLP 0057 (Rust standard library and boundary), LLP 0058 (engine seam), LLP 0058.000.000 (capability-context and adapter protocol), LLP 0058.000.001 (greenfield kernel construction), LLP 0013 (current per-package compartments and Hermes patch stack), LLP 0021 (typed effect model and staged authorization), LLP 0039 (secure and insecure postures), LLP 0040 (runtime-extension context carriers), LLP 0059.000 (v1 API contracts)

## Summary

Ibex 2 should target a pinned, unmodified upstream Hermes instead of the
current Ibex patch stack and move runtime capability enforcement to the Rust
standard-library boundary. Hermes executes JavaScript, supplies intrinsics and
garbage collection, and owns its job queue; it is not part of the
capability-security kernel.

The engine patches currently supply unforgeable package identity,
compartment-global resolution, and Promise-job provenance, which a stock JSI
host function cannot recover. Ibex 2 therefore stops inferring authority from
the JavaScript stack: Rust mints a generation-scoped capability context per
module binding, the engine adapter closes over it when creating a callable,
and JavaScript can invoke or pass the callable but cannot inspect, synthesize,
or retarget its context.

The result is boundary-and-handle security with bearer/object-capability
semantics:

- authority-bearing and identity-reading operations are absent from the shared
  real global;
- module-bound callables and opaque resource handles carry authority;
- async work retains its Rust context explicitly rather than reconstructing it
  from Hermes frames or Promise jobs;
- passing, exporting, or scheduling a bound callable or handle is explicit
  delegation (D5); and
- the vanilla shared realm protects host authority from compromised modules
  under a pre-project integrity contract, but does not isolate shared
  JavaScript objects, availability, or process state (D8).

## 1. Current state

Ibex currently builds a fork: pinned upstream Hermes plus the ordered
`patches/hermes/` stack `[observed]`. Receipts name `source-patched` or
`windows-source-patched`, and `build.rs` rejects artifacts lacking that patched
identity `[observed]` (`build_support/hermes_profile_provenance.rs`). Patches
0001–0008 provide attribution, compartments, lockdown, eval inheritance, and
scheduler capture; 0009–0015 preserve evaluation/async facts, external-buffer
aliases, constrained principals, no-eval behavior, and root-surface closure.

The first Rust stdlib slice moved semantics but not identity: timers and
`fs.readFile` call `currentPrincipalId()` and
`exactCollectTypedPrincipalStack()` before Rust `[observed]`; without patched
frame symbols the host falls back to a thread-local principal and still links
`[observed]`. Thus `CapabilityAuthorizer` is not yet independent of Hermes;
D7 forbids this fallback.

## 2. Proposed decision

### D1. Vanilla means zero Ibex source patches

The production engine is a pinned upstream Hermes commit built from an exact
source identity with **no Ibex patch applied to the Hermes source tree**.
Ibex-owned adapter C++ outside Hermes, upstream-supported build flags, and
content-addressed artifact receipts remain allowed. A downstream diff that
changes Hermes source, bytecode libraries, or private internal JavaScript is a
patch and violates this target even if applied only during the build. An Ibex
change accepted upstream ceases to be a patch once the selected pin contains
it, so upstreaming a needed primitive is a valid retirement path.

### D2. Runtime enforcement lives in Rust

Every capability-bearing v1 operation reaches a typed Rust dispatcher before
transport or ambient state. Rust owns the operation catalog and invocation
lane; runtime, context, buffer, callback, and resource-handle generations;
grants, denials, revocation, and delegation records; VFS and network
Requested/Discovery/Commit/Repeat authorization; timer ownership and
async-operation context retention; and fail-closed teardown and stale-handle
behavior.

Platform code may execute transport after Rust authorizes the exact stage. The
engine adapter may translate values, borrow buffers for a bounded call, and
enqueue completion work on the owner thread. Neither is an alternate policy
path. This moves runtime enforcement, not every CapSec artifact or tool:
policy authoring, conformance generation, review registries, and evidence
reports may stay declarative or use the most suitable build-time language.

### D3. Authority is bound, not stack-inferred

Rust mints a `CapabilityContext` for a runtime generation and principal. The
module loader asks Rust for operation bindings under that context. An engine
binding is a host callable whose native closure contains an opaque binding
handle. Invocation supplies only that handle and typed arguments; the adapter
never asks Hermes which frame is current.

The handle binds at least: exact runtime generation; principal and static
grant projection; dynamic/revocation generations the operation requires;
operation identity and invocation lane; and any explicit constrained-principal
or resource attenuation the binding carries. JavaScript never receives those
fields. A value exposed to JavaScript is not a context handle unless Rust
minted it and validates its generation and kind.

### D4. The shared global carries no authority and reads no identity

Pure APIs may remain shared globals, under two rules:

1. Every operation that reads caller or principal identity is
   capability-bearing — timers that carry an actor, filesystem, network,
   storage, crypto keys, and anything whose behavior or audit record depends
   on the invoking module. In the vanilla secure posture such operations are
   module-bound and absent from the shared real global. Today's `setTimeout`
   reads `currentPrincipalId()` from the real global and cannot survive there;
   `queueMicrotask` and other grant-free intrinsics can.
2. Whatever remains on the shared global neither infers caller identity nor
   confers grants.

Module factories receive bound callables as lexical parameters or through an
immutable module-scoped stdlib namespace. Bare `fetch` can be a module
binding; a shared `globalThis.fetch` cannot preserve per-module authority on
stock Hermes and is not published in the secure profile.

This is the decided secure v1 compatibility contract. Code that needs an
authority-bearing API specifically through `globalThis` must use the
explicitly named whole-runtime compatibility posture or consume the
module-bound surface instead. Ibex must not recreate per-module globals by
source rewriting while claiming the engine fork was removed.

LLP 0059.000's generic `hostCallInline(op, ...)` / `hostCallAsync(op, ...)`
notation is the adapter-to-Rust ABI behind fixed native closures, never a
JavaScript API that accepts an operation ID. Grant classification and
provenance are orthogonal: timers remain grant-free, but actor-retaining
schedule/clear/ref operations are identity-reading, `ContextRequired`, and
module-bound; `queueMicrotask` may remain shared. This delta and equivalent
opaque-resource/`CryptoKey` custody wording require an accepted LLP 0059.000
amendment before the vanilla profile flips.

### D5. Delegation is explicit, with bearer/object-capability semantics

This RFC decides bearer/object-capability semantics for the vanilla posture.
Deliberately passing, exporting, re-exporting, storing where another module
can read it, or scheduling — through `Promise.then`, a timer, an event
registration, or any other completion — an authority-closing callable or
resource handle delegates that binding. A bound callable invoked later from an
empty stack or detached completion is authorized as its binding. A callee
cannot amplify a delegated binding or retarget it to a different runtime,
operation, or resource; Rust applies any supported attenuation before minting
a derived handle.

This supersedes, for the vanilla tier, the deputy protections of patch 0008
(scheduler-principal intersection) and patch 0007 (detached-native denial).
`Promise.resolve(x).then(deputy.readFor)` denies today because the ungranted
scheduler is intersected; under bearer semantics it is delegation by whoever
held `readFor`, authorized as the binding. Those are LLP 0013 product claims,
not patch implementation details, so the flip requires accepted amendments
superseding LLP 0013's stack-intersection and detached-denial guarantees for
the vanilla tier — and qualifying any LLP 0039/0040 language relying on them —
or those guarantees remain only on the patched legacy tier of §7. The
amendment must also replace LLP 0013's frame-accurate recipient attribution:
raw bearer transfer is not attributable to its recipient unless Rust derives
and records a new delegation.

LLP 0040 is stricter still: it requires live ∩ acquisition constrained
principals for every capability class and refuses non-empty extension
registries without the patched carrier. Possession-only vanilla semantics do
not satisfy that contract. Authenticated runtime extensions therefore remain
on the patched tier until an accepted LLP 0040 amendment defines the Rust
binding/completion replacement and removes the patch-export installation gate.

Ibex 2 does not reconstruct an intersection of all JavaScript frames per call;
that would need engine provenance or equivalent hidden instrumentation and
preserve the complexity this RFC removes. The LLP 0057 §4 threat-model
ceiling stands as qualified: compromised dependencies cannot discover ambient
authority, and explicit handoff by authorized code is delegation, not a
sandbox escape.

### D6. Async context is data owned by Rust

An admitted async operation retains its capability context, runtime
generation, and resource handles until completion or cancellation. A timer
retains the context of its bound timer operation. A network or filesystem
completion returns through a generation-checked completion token. The adapter
enqueues a task onto the exact owner thread and lets Hermes perform the
microtask drain its Promise semantics require.

Retained context is consumed only by the completion that owns it. It is never
installed as a thread-local or ambient "current module" around arbitrary
JavaScript, and no security decision depends on walking a callback's frames or
observing a Promise scheduler. Engine job metadata may serve diagnostics only
if its absence cannot widen authority.

### D7. No engine-identity fallback

Patch 0007 exists because principal `0` on an empty stack was once trusted as
root, and the unpatched host links against a thread-local fallback (§1). The
vanilla secure artifact contains no `currentPrincipalId`, principal-stack,
thread-local identity, principal-zero, or ambient/root fallback path — not as
dead code, not as a link stub. An operation reaching the boundary without
Rust-minted provenance fails the build or fails closed; missing provenance is
never authorized as root or ambient. Gate §8.1 probes for these directly.

### D8. Integrity contract and exact adversary

Lexical authority is private only if shared machinery cannot interpose on its
use: a module that replaces `Promise.prototype.then` can capture privileged
callbacks that close over bound operations — discovery through shared state,
not handoff. The vanilla secure posture therefore requires a pristine,
pre-project integrity contract: before project code runs, the shared intrinsic
and global graph is frozen using stock public mechanisms, loader and bootstrap
machinery is unreachable from project code, and adversarial poisoning fixtures
prove both.

The vanilla adversary includes a malicious or compromised JavaScript module in
the authenticated graph. The claim is narrow: without a binding or delegated
handle it cannot discover, forge, or exercise host authority. Vanilla does not
protect shared JavaScript objects or live exports from mutation, prevent
denial-of-service, hide data another module deliberately exposes, provide
frame-accurate recipient audit, or contain an engine/native escape. The named
hostile-module tier adds compartments, constrained-principal/deputy rules, and
stronger audit; process/runtime isolation remains the boundary for truly
hostile code. Thus “supply-chain containment” here means undeclared host
authority containment, not general same-realm isolation.

## 3. Security model

### 3.1 In scope

The zero-patch profile must prevent:

- a malicious or compromised graph module invoking a capability-bearing
  operation without a minted binding or
  delegated handle;
- fabrication, cross-kind, cross-runtime, or stale-generation use of a context
  or resource handle;
- authority discovery through the shared global, intrinsic or prototype
  poisoning under D8, bootstrap residue, diagnostic bridges, or transport back
  doors;
- identity reconstruction through any D7-forbidden fallback;
- lookup-before-authorization for resources whose identity emerges in stages;
- async completion into a destroyed or different runtime generation; and
- transport execution after a denial, malformed context, or failed stage.

### 3.2 Explicitly out of scope

The profile does not prevent an authorized module from deliberately passing,
exporting, or scheduling a bound callable or handle; D5 defines that as
delegation. It does not infer callback-registration intent, recreate stack
inspection, or preserve scheduler-principal intersection. It does not isolate
shared-object/export integrity, availability, recipient attribution after raw
bearer transfer, or OS-process isolation from native extensions or a
compromised embedder. The claim is undeclared host-authority containment under
bearer semantics, not a general JavaScript sandbox.

### 3.3 No silent downgrade

If module-bound injection is unavailable for a module format or build path,
that path cannot run under the per-module secure profile. It may fail closed
or use a separately named whole-runtime/ambient posture governed by LLP 0039,
but must not silently bind every module to the root context. The secure build
remains patched until the replacement is complete; "vanilla Hermes" is not
evidence that the Rust boundary is complete, and a passing unarmed runtime is
not evidence for the secure profile.

## 4. Engine contract after the migration

The engine adapter owns only these security-relevant mechanics:

1. creating host callables that close over an opaque Rust binding handle;
2. preserving borrowed-buffer lifetime for bounded inline calls;
3. retaining JavaScript callbacks through generation-checked native handles;
4. enqueuing completions only on the exact runtime owner thread;
5. interleaving Rust tasks with engine microtasks per LLP 0058's job queue
   contract; and
6. removing construction-private adapters before project code executes.

It does not own grants, principal discovery, resource policy, redirect policy,
VFS stage decisions, or delegation semantics. An engine may offer richer
provenance for diagnostics, but the common seam cannot require a private
engine symbol to enforce authority. Promise, `async`/`await`, GC, error
stacks, `WeakRef`, and language semantics remain engine-intrinsic per LLP
0058; Rust owns the context attached to a host operation and does not replace
Hermes's job queue with a second Promise implementation.

## 5. Retiring the patch stack

Patch removal is evidence-driven: each row must name a replacement or an
explicitly revised product contract before the zero-patch profile becomes
authoritative.

| Patches | Purpose | Retirement route |
|---|---|---|
| 0001–0003 | Domain principal, frame attribution | D3 bound contexts and D7's fallback ban; needs the LLP 0013 amendment superseding frame attribution for the vanilla tier |
| 0004–0006 | compartment globals, eval inheritance, native lockdown | authority-global removal is D4; lockdown and eval-escape containment are met by D8 on the one-trust-domain tier and stay on the patched legacy receipt for hostile-module isolation; "upstream hardening" alone is not a contract |
| 0007–0008 | no-user refusal, scheduler-principal capture | superseded on the vanilla tier by D5/D6 via the same LLP 0013 amendment; retained on the patched legacy tier |
| 0009–0011 | trap-free thrown values, Empty completion, failed-job provenance | revise or reimplement the structured-evaluation contract over stock public engine behavior; no silent approximation |
| 0012 | keyed overlapping external buffers | Rust buffer/resource handles, an upstream public primitive, or an accepted copy with measured cost |
| 0013 | Promise-job constrained principals | D5/D6: Rust contexts on bound operations and native completion tokens; no authority inference from Promise jobs |
| 0014 | one-way eval latch, cached fast-path closure | drop the requirement, avoid dynamic authority on the real global, or consume an upstream fix; restricted no-eval runtimes stay patched until then |
| 0015 | empty disabled `HermesInternal` shell | select an upstream pin/configuration passing the root-surface acceptance suite, or upstream the cleanup |

The table is not permission to weaken LLP 0024, LLP 0040, or
restricted-runtime contracts, and LLP 0013 gets the same discipline: its
runtime claims are superseded by explicit accepted amendment or retained on
the patched legacy profile, never dropped silently. If stock Hermes cannot
support a contract, the owning LLP is amended, the feature stays on the
patched legacy profile, or the migration remains incomplete.

## 6. Migration plan

LLP 0058.000.001 supersedes the earlier in-place cutover strategy. The
architecture is implemented as a separate runtime family with a new
composition root, kernel, module bootstrap, and public-Hermes adapter. Audited
semantic leaves and platform services may be reused; the legacy engine path is
never a fallback beneath it.

### M0. Freeze contracts and source closure

Keep the patched runtime operational. Land the two child Specs, define the new
artifact's source/dependency closure, classify reusable components, and record
LLP 0013/0039/0040/0059.000 amendments or patched-tier gates. No existing
engine bridge is presumed reusable merely because a feature can disable part
of it.

### M1. Prove stock public interfaces

Build `upstream-pinned` independently with an exact empty-patch receipt. Before
general API work, prove public factory/HBC invocation, pre/post microtask
checkpoints, private native closure/host-object state, exception reporting,
lockdown, and destruction with queued jobs. Until all §8 gates pass, the
profile is oracle/experimental, cannot enter a secure artifact, and either
cannot run project code or is mechanically disclosed and trip-wired under LLP
0039.

### M2. Construct a deny-all Rust kernel

Create the LLP 0058.000.000 record tables, operation catalog, policy
generation, revocation, unified host-task FIFO, refusal taxonomy, and teardown
in an engine-independent crate. Run the protocol through a mock adapter. Do
not port `currentPrincipalId`, constrained-stack collection, scalar context or
resource handles, global installers, or the legacy generic dispatch surface.

### M3. Land the new module/bootstrap path

Compile every supported module to receipt-bound `FactoryV1`, inject an
immutable bound namespace, remove construction roots, execute deterministic
lockdown, and enter the exact outer driver. Direct-eval and pre-existing HBC
that expects authority globals refuse; no general source rewrite or root
fallback is introduced.

### M4. Prove the representative vertical slice

Implement `TextEncoder.encodeInto`, module-bound actor timers, promise-only
staged `fs.readFile`, and one opaque crypto-key operation, plus their
completion/revocation/teardown races. These run only through the new artifact.
Missing APIs stay absent instead of borrowing Ibex 1 implementations.

### M5. Expand by audited reuse

Classify each v1 operation as an adopted engine-neutral leaf, a wrapped typed
platform service, a rewritten boundary, or absent. Preserve existing VFS and
network Requested/Discovery/Commit/Repeat semantics and verified resource
facts. Close non-CapSec patch dependencies through public replacements,
accepted contract revisions, or patched-tier retention. A capability-bearing
family is not published until its complete transport and inventory path is
closed.

### M6. Cut over at the artifact boundary

After every gate passes for a declared application/API tier, a product may
select the whole greenfield runtime before allocation. It never selects
individual new operations inside a legacy runtime. Making it the default is a
separate product decision. The patched profile remains a named supported tier
while hostile-module, deputy/audit, extension, or other contracts require it;
its plumbing is deleted only after no supported artifact depends on it.

## 7. Product postures and compatibility

Engine profile and security posture are separate. This RFC maps onto Accepted
LLP 0039 rather than creating a third compatibility mode:

| LLP 0039 entry | enforcement and graph | engine eligibility |
|---|---|---|
| general CLI secure production | fail-closed per-module host-authority containment (D8) | patched until every vanilla gate and required amendment passes; then vanilla only when no selected policy requires patched deputy/extension contracts |
| secure development (`unadvertised-dev-arming`) | the same enforcement; only advertisement differs | the same engine eligibility as secure production |
| standalone ambient default (LLP 0047) | **AmbientCompatibility**: one application context, Web-shaped globals, no per-module claim, authenticated disclosure | vanilla is eligible because this is LLP 0039's already named ambient path, not a secure-profile fallback |
| standalone monotonic CapSec selector | the same secure eligibility and graph rules as the general CLI | patched or gate-complete vanilla, selected without downgrade |
| compile-time `insecure` | enforcement off, explicitly disclosed, never implicit | engine choice confers no security claim |
| policy requiring `deputyClasses`, frame-accurate recipient audit, or a non-empty LLP 0040 registry | patched hostile-module/deputy tier, or separately accepted process/runtime replacement | vanilla refuses until the owning LLP amendment is accepted |

One executable supports several rows only through the selector and disclosure
rules in LLP 0039/0047. A vanilla engine artifact never selects or upgrades a
security posture by itself.

## 8. Acceptance gates

The default may flip only when all of the following hold.

### 8.1 Engine and build identity

- Hermes source at build time equals the pinned upstream tree.
- The engine receipt proves an empty local patch set and binds the mapped
  artifact on every supported platform.
- No required symbol or header is supplied only by `patches/hermes/`.
- The selected stock pin proves, through public interfaces only, the factory
  invocation and microtask-checkpoint operations required by LLP 0058 and the
  child Spec.
- Negative packaging and selector tests prove an oracle-class receipt cannot
  enter a secure artifact before every gate passes.
- No `currentPrincipalId`, principal-stack, thread-local identity, or
  principal-zero/ambient fallback symbol or path exists in the vanilla secure
  artifact (D7).
- A clean build never reads the patch directory as an input.

### 8.2 Boundary completeness

- Every capability-bearing v1 operation joins exactly one Rust operation and
  authorization path. The greenfield artifact links no legacy fallback, and
  unimplemented operations are absent.
- No engine adapter or platform transport can execute the effect after a Rust
  refusal.
- Context, callback, buffer, and resource handles reject wrong kind, stale
  generation, wrong runtime, and use after teardown.
- VFS and network stage tests bind decisions to the exact discovered and
  committed resources.

### 8.3 Package containment

- An authenticated dependency cannot acquire undelegated authority through
  `globalThis`, bootstrap residue, constructor walks, `eval`, `Function`,
  intrinsic or prototype poisoning, a Promise continuation, a timer, or a
  detached callback.
- A module receives only its own bound operation set plus explicit
  delegations.
- Fixtures distinguish delegation from discovery, including the
  detached-deputy case (`Promise.resolve(x).then(deputy.readFor)`), authorized
  as the binding under D5 rather than denied as under patch 0007.
- Unsupported module formats and dynamic source paths refuse rather than bind
  root authority.
- Every supported source/prepared/HBC artifact matches the child Spec's
  receipt-bound factory ABI; all other shapes refuse before project code.

### 8.4 Engine semantics

- Promise/microtask ordering passes the application-tier engine seam suite.
- Structured evaluation, rejection reporting, external buffers, restricted
  no-eval construction, and the disabled `HermesInternal` surface each match
  their owning accepted contract or an accepted replacement contract.
- The supported application corpus passes from shipped Hermes bytecode.

### 8.5 Cross-platform evidence

The acceptance suite runs against the exact upstream artifact for macOS, iOS,
Android, Linux, and Windows, subject to the platform matrix's supported tiers.
Evidence from one source build does not bless a different AAR, framework,
DLL, or static archive.

### 8.6 Closed-world effect inventory

For each shipped posture, an artifact-wide inventory enumerates every
reachable capability effect path — v1 operations, legacy and Ibex 1 spellings,
native extensions, diagnostics, bootstrap bridges, platform entry points, and
direct transports — and proves each is absent, refuses, or joins exactly one
Rust authorization path. The gate is closed-world: a reachable path missing
from the inventory fails it; sampling known paths is insufficient. This makes
R4's surface inventory and effect-path joins mandatory.

### 8.7 Owning-contract gates

Before vanilla becomes secure-selectable, accepted corpus changes must map
LLP 0013 deputy/audit semantics, LLP 0039 posture selectors, LLP 0040 extension
carriers, and LLP 0059.000 lane/timer semantics to this architecture. Until
then the relevant feature or policy remains patched or unavailable; prose in
this RFC is not itself an amendment to an Accepted or separately governed
contract.

## 9. Risks

The main risks are the D4/D8 compatibility break for reflective globals and
polyfills; loader scope creep into a source-rewriting compartment system;
loss of structured-evaluation facts exposed by patches 0009–0011; false
confidence while any path bypasses Rust (§8.6); and tighter dependence on
upstream Hermes behavior. Corpus measurement, the small factory contract,
owning-LLP gates, the closed-world inventory, and pin-level conformance are
the respective controls.

## 10. Alternatives considered

Keeping all patches retains implicit attribution but leaves Hermes in the
security kernel. One runtime per package provides stronger isolation but
turns object identity and callbacks into cross-runtime protocols, so it is a
hostile-module-tier option. Rewriting free globals recreates a compiler fork;
only the bounded factory/namespace binding is allowed. A whole-runtime
principal drops per-package containment and belongs to the compatibility
posture.

## 11. Resolved questions and remaining open items

Resolved in this revision: the module-bound, no-authority-global secure v1
compatibility contract (D4); bearer/object-capability deputy semantics, with
stack intersection and detached-native denial surviving only on the patched
legacy tier via explicit LLP 0013 amendment (D5); the narrow malicious-module
host-authority claim of the vanilla shared realm, with shared-object,
deputy/audit, and stronger hostile-module containment on the patched or
isolated-runtime tier (§7); and retention of the patched profile as a
supported legacy receipt class while any tier needs it, with plumbing deleted
only afterward (M6).

Remaining open, deferrable because the owning contracts already fail closed:

1. Whether Ibex 2 preserves every LLP 0024 structured-evaluation distinction
   or narrows that ABI under a new stock-engine contract (§8.4 blocks the flip
   until an accepted contract exists).
2. Whether restricted no-eval construction ships in the first vanilla release
   if the selected pin retains the patch 0014 fast-path behavior (restricted
   runtimes stay patched until it does).

## 12. Child specification ownership

Two child Specs jointly close this RFC:

- LLP 0058.000.000 owns the engine-independent security protocol: records,
  private tokens, invocation, module binding, delegation, async delivery,
  task/microtask ordering, teardown, refusals, and conformance.
- LLP 0058.000.001 owns the greenfield construction: component dependency
  graph, reuse audit, build/source isolation, vertical slice, work gates,
  no-hybrid rule, and artifact-level cutover.

An implementation must satisfy both. Construction convenience cannot weaken
the protocol, and protocol conformance in a mock does not prove that the
shipped artifact excludes legacy paths. Neither Spec may assume a
Hermes-private symbol; stock-public feasibility remains an acceptance gate.
