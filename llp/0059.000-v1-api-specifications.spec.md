# LLP 0059.000: v1 API specifications

**Type:** Spec
**Status:** Draft
**Systems:** Runtime, Host ABI, CapSec, Engine
**Author:** Charlie Cheever / Claude (Opus 5)
**Date:** 2026-08-27
**Revised:** 2026-08-27 (initial draft)
**Related:** LLP 0059 (the measured inventory this specifies), LLP 0057 (Ibex 2 — the boundary rule), LLP 0058 (the engine seam), LLP 0039 (secure and insecure modes — the arming posture grants inherit)

## Summary

LLP 0059 says which APIs Exact uses. This says what to build: for each one, the
surface, which side of the boundary owns what, its capsec posture, and what is
deliberately partial in v1.

Entries carry their provenance. **Measured** means LLP 0059 found it in
application code. **Author-required** means Charlie named it as something to
build on — a requirement, not a prediction, and the only kind of unmeasured
entry §7 admits. Both are v1; the marker exists so a later reader does not
mistake one evidence standard for the other.

Every API here is one of three shapes, and the shape decides most of the rest:

- **Pure** — computed entirely in Rust, no platform call, no capability. `URL`,
  `TextEncoder`, `atob`, `structuredClone`.
- **Delegating** — Rust owns semantics, the platform owns transport. `fetch`.
- **Ambient** — reads or writes process- or device-scoped state. `process.env`,
  `localStorage`, `crypto`. These are the capability-bearing ones.

## 1. The host-call boundary

One surface. Every Tier I API reaches Rust through it.

```
hostCall(op: u32, args: HostValue[]) -> HostResult
```

Four properties, all cheap now and expensive to retrofit:

1. **Primitives and handles only.** Numbers, strings, `ArrayBuffer`s, and opaque
   handles. No JSON at the boundary; a `fetch` that serializes has traded parse
   time for call time.
2. **Async by default** (LLP 0297). `hostCall` returns a promise. The
   synchronous variant exists only for the exceptions in §2 and each one is
   named there — there is no general sync surface.
3. **The capability check is here.** One chokepoint, before dispatch. This is
   the whole of LLP 0057 §4: an operation either carries a grant or is refused,
   and no capability is reachable by any other path.
4. **Buffers cross by handle, not by copy**, wherever the operation's lifetime
   allows it.

## 2. Synchronous exceptions

Sync cross-thread calls are forbidden by default. Two APIs in §3 are
synchronous by their own contract and cannot be made async without breaking
application code:

- **`localStorage`** — the web contract is synchronous. It must not become a
  cross-thread blocking call. **v1 resolution: the store is mirrored into the
  engine's realm at boot and written through asynchronously.** Reads hit the
  mirror; writes update the mirror synchronously and enqueue a durable write.
  The cost is that a write is not durable when the call returns, which is
  acceptable for the measured uses (22 uses across 7 modules, all UI
  preference state) and must be stated in the binding's documentation.
- **`performance.now`** — sync, but it reads a clock rather than calling a
  service. **v1 resolution: a shared-memory read of the frame clock's time
  base**, not a host call. It must be the same base the host uses for
  `requestAnimationFrame` and motion, or animation and scheduling drift.

Any third candidate needs an entry here and a reason. That list is the whole
exception surface.

## 3. The APIs

### 3.1 `console` — pure, ungated

`log` `warn` `error` `info` `debug`. Formatting happens in Rust so it is
identical across engines. **Non-blocking**: writes enqueue and flush on a
timer or at a size threshold. 214 uses across 89 modules makes this the most
frequently called API in the system; a synchronous flush per call is a
startup regression on its own.

Out of v1: `table`, `group`, `time`, `trace`, `dir`, `count`, `assert`.

### 3.2 Timers — pure, ungated

`setTimeout` `setInterval` `clearTimeout` `clearInterval`. Integer handles.
Clamping and ordering follow the HTML spec: same-delay timers fire in
insertion order. The timer wheel lives in Rust; expiry enqueues a task into
the engine job queue through the LLP 0058 §3 adapter.

Out of v1: `setImmediate`, `requestIdleCallback`.

### 3.3 `TextEncoder` / `TextDecoder` — pure, ungated

`TextEncoder`: `encode`, `encodeInto`. `TextDecoder`: `decode` with `stream`.
**UTF-8 only in v1.** The measured uses are all UTF-8; `latin1`, UTF-16, and
the legacy label set are out. `fatal` and `ignoreBOM` are honored.

Buffers cross the boundary by handle. `encodeInto` writing directly into a
caller-supplied `Uint8Array` is the reason `ArrayBuffer` handles are in the
boundary contract at all.

### 3.4 `URL` / `URLSearchParams` — pure, ungated

Full WHATWG URL parsing, including IDNA and percent-encoding rules, because a
partial URL parser is a security bug rather than a missing feature. This is
pure Rust and should be a well-tested crate rather than hand-written.

`URLSearchParams`: construction from string, object, and pairs; `get`,
`getAll`, `set`, `append`, `delete`, `has`, iteration, `toString`.

### 3.5 `fetch` — delegating, **capability-bearing**

The largest v1 item, and understated by its twelve call sites: a `Response`
implies `Headers`, body accessors, redirect policy, and abort.

**Rust owns:** header name case-folding and the forbidden-header list, redirect
following and its count limit, the body state machine, `AbortSignal`
integration, and the error taxonomy — so failures are identical on every
platform.

**The platform owns:** sockets, TLS, proxy configuration, HTTP/2 and /3,
connection pooling, and the system certificate store.

v1 surface: `fetch(input, init)` with `method`, `headers`, `body`, `signal`,
`redirect`. `Response`: `status`, `ok`, `headers`, `url`, `text()`, `json()`,
`arrayBuffer()`, `blob()`. `Headers` and `Request` constructible.

Out of v1: streaming request bodies, `ReadableStream` response bodies (buffer
whole, per §5), `cache` and `credentials` modes, `FormData` bodies, service
workers.

**Capability:** `net.fetch`, granted per-origin. This is the operation the
supply-chain story is about; a package without the grant cannot reach the
network by any path, because there is no other path.

### 3.6 `AbortController` / `AbortSignal` — pure, ungated

`abort(reason)`, `signal`, `aborted`, `reason`, `addEventListener('abort')`,
`AbortSignal.timeout`, `AbortSignal.any`. Mostly engine-side; the only Rust
concern is propagating a signal into an in-flight `fetch`.

### 3.7 `localStorage` — ambient, **capability-bearing**

`getItem` `setItem` `removeItem` `clear` `key` `length`, plus index access.
Strings only. Mirrored per §2. Scoped per application, not per package.

**Capability:** `storage.local`. Out of v1: `sessionStorage`, the `storage`
event, quota reporting.

### 3.8 `process.env` — ambient, **capability-bearing**

Read-only. Returns a snapshot object, not a live proxy.

**Capability:** `env.read`, granted per-variable-name. This is the canonical
supply-chain case — a package reading `AWS_SECRET_ACCESS_KEY` — and a
per-variable grant is what makes the refusal meaningful rather than
all-or-nothing.

Out of v1: writes, `process.argv`, `process.cwd`, `process.exit`, everything
else on `process`.

### 3.9 `crypto` — ambient, partially gated

`crypto.randomUUID()` and `crypto.getRandomValues()`. Both draw from the
platform CSPRNG. **Ungated** — neither conveys authority, and gating them
would train people to grant capabilities reflexively, which is how a
capability system dies.

Out of v1: all of `crypto.subtle`. LLP 0059 §6 measured it as entirely
server-side.

### 3.10 `atob` / `btoa`, `structuredClone`, `Blob`, `CustomEvent` — pure, ungated

`atob`/`btoa`: base64 in Rust, throwing on invalid input per spec.

`structuredClone`: the structured clone algorithm over the engine's value
space — objects, arrays, `Map`, `Set`, `Date`, `RegExp`, typed arrays, and
cycles. **No transferables in v1** (one measured use).

`Blob`: constructor, `size`, `type`, `text()`, `arrayBuffer()`, `slice()`.
Required by vendored Rive and Lottie, not by first-party code.

`EventTarget` / `CustomEvent`: `addEventListener`, `removeEventListener`,
`dispatchEvent`, with capture and `once`. Engine-side; no Rust component.

### 3.11 `fs` — delegating, **capability-bearing** *(author-required)*

Promise-based only. `readFile` `writeFile` `appendFile` `readdir` `mkdir`
`rm` `stat` `rename` `copyFile` `realpath`, each returning a promise, plus
`createReadStream`-shaped iteration deferred with the rest of streams (§5).

**No synchronous variants.** `readFileSync` and its family are the largest
single source of blocking in Node programs, and LLP 0297 forbids the
cross-thread sync call they would require. This is a deliberate divergence
from Node and should be documented as one.

Paths resolve through the existing virtual filesystem namespace rather than
the raw OS path space, so a grant is expressible as a subtree.

**Capability:** `fs.read` and `fs.write`, **granted per path prefix**. This is
the second half of the supply-chain story — the package that cannot read
`~/.ssh` — and per-prefix is what makes it meaningful rather than a single
all-or-nothing switch.

### 3.12 `WebSocket` — delegating, **capability-bearing** *(author-required)*

The WHATWG interface: constructor with protocols, `send` (string,
`ArrayBuffer`, `ArrayBufferView`, `Blob`), `close(code, reason)`,
`readyState`, `bufferedAmount`, `binaryType`, and the `open` `message` `error`
`close` events.

**Rust owns:** framing, the closing handshake, ping/pong, backpressure
accounting, and the close-code taxonomy. **The platform owns:** the socket,
TLS, and proxy traversal — the same split as `fetch` §3.5.

Ibex already speaks WebSocket internally for the dev connection. That is a
runtime-internal transport; this is the application-facing binding, and they
should share the Rust implementation rather than growing a second one.

**Capability:** `net.websocket`, per-origin.

Out of v1: subprotocol negotiation callbacks, `permessage-deflate`.

### 3.13 `Buffer` — pure, ungated *(author-required)*

A `Uint8Array` subclass, as in Node, so a `Buffer` is accepted anywhere a
typed array is.

v1: `Buffer.from` (string with encoding, array, `ArrayBuffer`, `Buffer`),
`Buffer.alloc`, `Buffer.allocUnsafe`, `Buffer.concat`, `Buffer.isBuffer`,
`Buffer.byteLength`; and on the instance `toString(encoding)`, `slice`,
`subarray`, `equals`, `compare`, `indexOf`, `includes`, `fill`, `write`, and
the fixed-width `read*`/`write*` numeric accessors.

Encodings: `utf8`, `hex`, `base64`, `base64url`, `latin1`, `ascii`. The
conversions are Rust; the object is engine-side.

Worth stating plainly, since it will be asked: `Uint8Array` covers most of
what `Buffer` does, and `Buffer` is a Node-ism the web platform never adopted.
It is in v1 because it is materially more ergonomic for byte manipulation and
the author intends to use it, not because the measurement demanded it.

### 3.14 `crypto.subtle` — pure, ungated *(author-required)*

Operations on caller-supplied key material. Ungated for the same reason as
`getRandomValues` (§3.9): computing a digest conveys no authority, and gating
harmless operations trains people to grant reflexively.

v1: `digest` (SHA-256, SHA-384, SHA-512); `importKey` and `exportKey` (`raw`,
`pkcs8`, `spki`, `jwk`); `sign` and `verify` (HMAC, ECDSA P-256, Ed25519);
`encrypt` and `decrypt` (AES-GCM); `deriveBits` and `deriveKey` (HKDF,
PBKDF2); `generateKey` for the above. `CryptoKey` is an opaque handle whose
material never crosses into the engine unless the key is `extractable` and
`exportKey` is called.

Backed by the vetted crate already vendored in this repository rather than a
new implementation. **SHA-1 and MD5 are not provided**, in either direction.

Out of v1: RSA in all forms, AES-CBC and AES-CTR, X25519 key agreement,
`wrapKey`/`unwrapKey`. A persistent key store is out and would be
capability-bearing when it arrives — the operations are harmless, but custody
of a key is authority.

### 3.15 SQLite — host module, **capability-bearing** *(already built)*

Not standard-library surface, and listed here so it is not re-implemented as
such. `@exact/sqlite` is already a typed JavaScript wrapper over a native
module reached through `ModuleRegistry` — the LLP 0057 pattern, working today,
and not boot-eager.

v1 keeps it exactly as it is. What changes is that its native side becomes an
ordinary consumer of the §1 boundary, and it gains a grant.

**Capability:** `sqlite.open`, per database path. Prefer the async surface;
the existing sync methods keep their LLP 0297 exception note.

## 4. Capability summary

| API | capability | granularity |
|---|---|---|
| `fetch` | `net.fetch` | per-origin |
| `WebSocket` | `net.websocket` | per-origin |
| `fs` | `fs.read` / `fs.write` | per path prefix |
| `localStorage` | `storage.local` | per-application |
| `process.env` | `env.read` | per-variable |
| SQLite | `sqlite.open` | per database path |
| everything else in §3 | none | — |

Six capabilities, and the three that carry the supply-chain story are
`net.*`, `fs.*`, and `env.read` — network egress, filesystem reach, and
secrets. `crypto.subtle` and `Buffer` are deliberately ungated: they compute,
they do not reach. Compare the current design, whose registry is 4.16MB and
whose remaining admission work LLP 0039 records as roughly 16,628 unresolved
rows. The reduction is not a simplification of policy; it is what happens when
the enforcement point stops being every bare global reference.

## 5. Standing v1 exclusions

Applying to every API above rather than repeated per entry: **no streams**
(`ReadableStream`, `WritableStream`, `TransformStream`), **no workers**, **no
`SharedArrayBuffer` or `Atomics`**, **no `WebSocket`** (LLP 0059 §6). Bodies
buffer whole. Streaming returns when an application needs it and can say what
for.

## 6. Growth

Per LLP 0059 §7: a measured call site in application code — or the author
naming it as something to build on, which is a requirement rather than an
anticipation, and is marked *author-required* where it appears. Each addition names its shape from the Summary, its capability or its
absence, and its sync exception or its absence. An API that cannot state those
three is not specified yet.
