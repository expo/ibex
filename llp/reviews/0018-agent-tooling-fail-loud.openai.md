# Review: LLP 0018 - Agent Tooling Should Fail Loud, Not Silent-Green

**Reviewer family:** OpenAI
**Provider / runtime:** Codex / GPT-5
**Date:** 2026-07-05
**Redacted:** No - the review was performed against local repository sources in this checkout.
**Method:** Direct local review. I read LLP 0018, LLP 0000, the LLP 0005 review guide, LLP 0006, LLP 0017, the existing 0017 review artifacts, and the live repo surfaces cited by the plan (`scripts/link-worktree-artifacts.sh`, `scripts/with-timeout.sh`, `scripts/check-generated-drift.sh`, `scripts/regenerate-vendored.sh`, `build.rs`, `Cargo.toml`, `package.json`, and `vendored-generated/README.md`). This Codex session did not author the draft.

## Overall assessment

Revise and stay `Draft`.

The plan is a good follow-on to LLP 0017. The governing rule is crisp, the highest-priority script bug is real in the current checkout, and the plan correctly preserves the two constraints that matter most: no shared mutable Cargo target directory, and no hidden bun/node dependency in a normal hermetic build.

I would fix three issues before treating it as ready for implementation. The most important is that item 5 currently permits a warning-only stale-vendored path, which does not satisfy the plan's own rule for agent-facing verification. The second is that item 7 makes "no rebase conflicts touching my files" carry too much correctness weight. The third is that the test wrapper's target-selection and parsing contract needs to be precise enough that it cannot become a new false-green surface.

## Strengths

- **Summary and governing rule** name the right abstraction: the failure is not "tooling is inconvenient," it is "exit 0 lied about the postcondition." That framing usefully covers symlinks, zero tests, stale generated bytes, and wrapper prerequisites.
- **Plan item 1** matches the live script. `scripts/link-worktree-artifacts.sh` currently anchors `repo_root` to `BASH_SOURCE` and prints `Done: 0 linked, N skipped` with exit 0, so changing destination resolution plus asserting required artifacts is the right fix.
- **Plan item 2** addresses a real verification hazard in this crate layout. The package has a lib target plus a binary target, and a filtered `cargo test --bin ibex ...` can miss lib/integration tests while still exiting successfully.
- **Constraints from existing LLPs** are well chosen. The plan keeps LLP 0017's single-writer rule for `target/` and LLP 0005/0006's hermetic default intact.
- **Sharp edges appendix** is useful operational memory. The integration-test C++ linkage note and the three-dot diff note are exactly the sort of small repeated failure that belongs near the agent playbook.

## Concerns

- **C-1 (medium/high) - Item 5 can still be silent-green for agents if stale vendored artifacts only warn.** The governing rule says an agent-facing verification command "must not exit 0" when its postcondition is unmet, and item 8 prefers checks built into exit status. But item 5 allows a `cargo build` warning, with failure only under an opt-in strict flag. For humans, a warning may be the right compatibility trade-off. For agents, a warning in build output is exactly the class of signal this plan says not to rely on. **Resolves when:** item 5 distinguishes consumer/human builds from agent/dev verification and makes the agent path nonzero by default, for example through `IBEX_FAIL_ON_STALE_VENDORED=1`, `IBEX_AGENT_STRICT=1`, or a wrapper that all playbooks use. Acceptance should include a stale `src/builtins/*.js` edit causing the agent verification command to fail nonzero while the hermetic default still avoids regeneration and bun/node.
- **C-2 (medium) - Item 7's post-rebase skip rule is too broad.** A conflict-free rebase that does not touch the agent's changed files can still introduce dependency, build-script, generated-artifact, platform, or test changes that break the agent's patch. The plan says targeted re-run suffices when the base only advances, but "no conflicts touching my files" is not enough evidence that the base change is irrelevant. **Resolves when:** item 7 defines a minimum post-rebase verification policy: always rerun the directly affected test/build command and drift check; require broader verification when upstream changed `Cargo.toml`, `Cargo.lock`, `build.rs`, generated artifacts, scripts used by the workflow, tests for the touched subsystem, or shared native files; and treat `sccache` as the primary cost reducer rather than correctness dilution.
- **C-3 (medium) - The zero-test wrapper contract needs to avoid excluding valid targets or masking failures.** The plan says "lib + integration tests, not `--bin` alone," but this repo also has substantial binary unit tests under `src/bin/ibex/`. If `scripts/run-tests.sh` implements the default as only `--lib --tests`, it will fix one blind spot while creating another. The parsing step also needs to preserve the real `cargo test` status when tests fail before all `test result:` lines are printed. **Resolves when:** the plan specifies default target selection as Cargo's normal package test set unless a `--scope lib|bin|test|all` option narrows it explicitly, and the wrapper acceptance tests cover zero matches, lib-only matches, bin-only matches, failing tests, and multiple test binaries.
- **C-4 (low/medium) - Required artifact semantics for item 1 should be explicit.** The plan says `--require ios/Frameworks,tools/hermes` or a default set, while the live script also links `node_modules`. If a required artifact is absent from both source and destination, the script should fail with the missing source/destination postcondition, not just "skip" and then maybe fail generically. If `node_modules` is optional but Hermes artifacts are required for native builds, that should be encoded. **Resolves when:** item 1 names the default required set by platform/profile, defines how `--require` interacts with source-missing artifacts, and keeps optional convenience links separate from required build postconditions.

## Suggestions

- Add the strict stale-vendored mode to sequencing as part of P1, not as a later playbook detail. This is one of the three silent-green bugs, so it should land with an executable acceptance test.
- Make `scripts/check-build-machine.sh` a script rather than only a playbook section. It can run the actual wrapper (`scripts/with-timeout.sh 1 true`), check `sccache --version`, verify `RUSTC_WRAPPER`/`SCCACHE_DIR`, and confirm the LLP 0017 hook default without relying on prose.
- Include `src/builtins/helpers/runtime-module-manifest.cjs` explicitly in item 5's path set. The current `check-generated-drift.sh` already treats it as a generated module-manifest output, and the stale-build check should not forget it.
- Consider making the landing helper in item 7 record the command evidence it is relying on before pushing. That would make "bounded retries" and "no full re-verify" auditable rather than another convention agents can misapply.
- If the fail-loud rule survives this implementation, promote a short version into LLP 0006 or the agent instructions. LLP 0018 can remain the implementation plan, but the rule is broader than this plan's tasks.

## Open questions

- Should the canonical agent entry point be only `scripts/run-tests.sh`, or should there also be a broader `scripts/cargo-agent.sh` / `scripts/verify-agent.sh` that sets strict stale-vendored checks and timeout behavior?
- Should normal `cargo build` warn on stale vendored inputs while agent verification fails, or should local dev builds fail by default once a source edit is detected?
- How will the landing helper know which upstream changes are irrelevant after a rebase: merge-base path diff, saved pre-rebase evidence, a touched-subsystem map, or a simpler always-run-targeted-check rule?
- Should hot-file serialization be handled socially by the coordinator/Linear workflow, or mechanically by a lightweight lock/queue in the landing helper?

## Recommended next step

Revise LLP 0018 to address C-1 through C-4 and keep `Status: Draft`. After those edits, the plan is probably ready for implementation with the current OpenAI-family review as one review artifact. Because this plan changes the commands agents rely on to verify and land code, a fresh implementation-time review of the actual shell/build patch would still be worthwhile.
