# Review of LLP 0071 r1 (75b8ba9) — GPT-6-Astra, xhigh

Run: `codex exec -m gpt-6-astra -c model_reasoning_effort="xhigh" --sandbox read-only`, 2026-10-07, blind to the other review. Final message verbatim.

Audited commit `75b8ba9` by static inspection. D1 and D2 address real gaps; D3 needs a stronger clock contract. D4’s event-delivery claim is true today. The RFC is not sufficient as written.

1. **MATERIAL — D3 introduces a caller callback under the timer lock.**  
   `RuntimeState::set_timer` locks `timers` before evaluating `self.now()`. Simply replacing `now()` with the supplied function therefore calls arbitrary caller code while holding that mutex. Reentry or lock inversion can deadlock. Admission and deadline queries already sample time before acquiring the timer lock; I found no existing `now()` call under the FIFO lock. See [task.rs:1006](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1006), [task.rs:1024](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1024), and [task.rs:1041](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1041).

   Specify that the callback runs outside Ibex locks, including any new clock/clamp mutex. Specify its thread, reentrancy, and panic contracts too. Built-in socket workers currently publish events without reading this clock, but Rust `Context` queries have no owner-thread restriction; `Send + Sync` does not promise invocation only on the JS thread. A callback panic reached through `performance.now()` or timer creation would encounter an `extern "C"` boundary without Rust panic containment; C++ exception handling does not solve that. See [bindings.rs:567](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings.rs:567), [boundary_abi.rs:320](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/boundary_abi.rs:320), and [boundary_abi.rs:614](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/boundary_abi.rs:614).

2. **MATERIAL — The monotonic clamp does not make arbitrary `f64` clock values safe. Admission can fail to terminate.**  
   The wheel converts milliseconds to `u64` microseconds and uses saturating deadline addition. A positive infinity, or a sufficiently large finite clock reading, saturates both “now” and subsequent interval deadlines to `u64::MAX`. The interval remains due every time it is rescheduled, so `admit_due_timers()` loops indefinitely. A maximum-ever clamp can also preserve a bad reading permanently. Define valid clock values, representable range, invalid-value handling, and synchronization of the clamp. See [timers.rs:88](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/stdlib/timers.rs:88), [timers.rs:111](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/stdlib/timers.rs:111), and [task.rs:1027](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1027).

   There is also an **existing**, directly relevant termination bug: `setInterval(f, 0)` reschedules at the same sampled time forever during one admission call. Sub-microsecond intervals can truncate to the same result. `MIN_DELAY` is zero, and JS accepts zero. D2 cannot safely promise unrestricted forwarding without addressing or explicitly constraining this behavior. See [timers.rs:68](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/stdlib/timers.rs:68) and [timers.js:34](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/timers.js:34).

3. **MATERIAL — D1/D2 omit the complete caller-driver contract: a pre-checkpoint and protection against nested delivery.**  
   The RFC specifies admission, delivery, then a checkpoint. The owning driver instead guards the entire cycle, drains existing microtasks, admits timers, delivers one task, and drains again. That ordering is required by LLP 0058.000.000 §8. For example, an already-queued Promise reaction that clears a due timer must run before its callback. Following the RFC’s recipe can fire it first. See [RFC:45](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:45), [hermes_shim.cc:535](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/src/engine/hermes_shim.cc:535), and [LLP 0058.000.000:449](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:449).

   Calling `fire_timer` after reservation is otherwise appropriate: no timer lock remains held, so callbacks can clear and schedule timers. But neither `fire_timer` nor `deliver_one` guards against a callback synchronously requesting another delivery. “One task per call” permits nested calls; the spec prohibits nested host tasks. Require an owner-thread driver guard spanning both checkpoints and delivery, or provide equivalent enforcement. See [install.cc:2133](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/install.cc:2133), [install.cc:2308](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/install.cc:2308), and [LLP 0058.000.000:466](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:466).

4. **MATERIAL — D2’s “Admission does not wake” is false and contradicts the existing wake contract.**  
   Timer admission calls `queue.admit`, which notifies the condition variable and may synchronously invoke the wake callback on the admitting thread. It releases the timer and queue locks first. Scheduling a timer, and merely advancing an external clock, do not generate that notification. These are different operations. See [RFC:64](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:64), [task.rs:1031](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1031), [task.rs:203](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:203), and [task.rs:230](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:230).

   Correct the statement rather than silently changing admission behavior. LLP 0068 specifies admission-triggered, coalesced notifications and requires the callback only to schedule and return. Incorrectly promising no callback could encourage callers to hold an executor lock across admission. See [LLP 0068:339](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0068-the-standard-library-for-a-rust-consumer.spec.md:339).

5. **MATERIAL — The RFC inherits an unacknowledged interval-commit conflict with LLP 0058.000.000.**  
   The spec says intervals reschedule **on delivery commit**, and failed admission leaves a timer eligible. Actual code removes/reschedules timers during `admit_due_timers`, before queue insertion and potentially well before delivery. D2 endorses that implementation without declaring this amendment. See [LLP 0058.000.000:551](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:551), [task.rs:1018](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1018), and [timers.rs:117](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/stdlib/timers.rs:117).

   This is observable: admitting an interval at 25, advancing to 60, and admitting again before delivery can queue two occurrences of that interval. Choose and document the intended commit/rescheduling semantics, including repeated admission without delivery. This discrepancy predates the RFC, but the RFC must reconcile it.

6. **MATERIAL — D3 does not ensure that the installed `performance.now` uses the supplied clock, and overlooks another spec amendment.**  
   `timers.js` installs its function only when `global.performance.now` is absent. A borrowed realm with an existing implementation keeps that clock while Ibex timers use the caller’s clock. Specify replacement, refusal, or an explicit prerequisite; otherwise D3’s shared-clock guarantee is false. `events.js` also captures the selected function for event timestamps. See [timers.js:96](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/timers.js:96) and [events.js:30](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/events.js:30).

   Additionally, LLP 0059.000 **§2**, which the RFC does not identify as amended, requires `performance.now` to be a shared-memory read of the frame clock’s base, expressly not a host call. Current implementation already differs, but D3 formalizes another contract and must explicitly reconcile that text. See [LLP 0059.000:183](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0059.000-v1-api-specifications.spec.md:183).

7. **MINOR — The caller recipe needs distinct rules for sleeping, liveness, and “settled at this clock.”**  
   `is_idle()` is false whenever any future timer exists, and an open WebSocket counts as in-flight activity. A 25–30-second interval or persistent socket therefore prevents it from becoming true. It cannot be the agent’s “settled now” condition. Conversely, `wait()` observes only queued tasks and a real-time timeout; timer expiry alone does not signal it. See [task.rs:994](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:994), [task.rs:613](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:613), and [bindings.rs:562](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings.rs:562).

   Define draining currently ready work separately from waiting for selected I/O and retaining future work. Also, `millis_until_next_timer` measures **caller-clock milliseconds**; it is not automatically a real-time sleep duration for a held or accelerated clock. External clock advancement must schedule the owner thread when necessary.

   Excluding `Date` is a defensible boundary, but advancing timer time alone does not establish the RFC’s token-expiry/backoff use case. That requires the caller’s coherent epoch-based `Date` implementation, as D3 acknowledges. See [RFC:35](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:35) and [RFC:84](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:84).

8. **MINOR — D4 is correct for delivery, but omits an existing WebSocket lifecycle obligation.**  
   The path already works: socket workers publish subscription events, ABI task kind 3 carries them, and `deliver_one` invokes `deliver_event`. A borrowed-runtime test already verifies transport failure producing `error` and `close`. There is no missing owning-runtime socket pump to transplant. See [task.rs:620](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:620), [boundary_abi.rs:1254](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/boundary_abi.rs:1254), [install.cc:2320](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/install.cc:2320), and [embedding.rs:584](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/tests/embedding.rs:584).

   However, the owning runtime calls `Adapter::prepare_garbage_collection()` before explicit GC. That reconciles listener and queued-output keepalive roots; a borrowed owner must do the same. Otherwise a root retained for outbound data can remain after that data drains without another event. The borrowed fixture’s GC helper currently omits this call. Document and test this existing obligation. See [hermes_shim.cc:491](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/src/engine/hermes_shim.cc:491), [install.cc:2191](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/install.cc:2191), and [embedding.cc:295](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/tests/embedding.cc:295).

9. **MINOR — Clarify the clock’s configuration boundary and fix the installation recipe.**  
   Refusing replacement after installation is correct for ordinary JS-created timers. Specify the refusal result, when installation seals configuration, and how earlier clock reads or Rust-created timers affect eligibility. Existing installation state lives in C++, while the proposed setter lives in Rust; enforcement must cover both sides. Existing deadlines must never silently change clock domains. See [RFC:70](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:70) and [install.cc:1563](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/install.cc:1563).

   Section 5 currently says to install and then set the clock, reversing D3. Its named group set also omits required dependencies: `TIMERS` requires `CONSOLE`, and `EVENTS` requires `PURE`; dependencies are refused rather than added automatically. State the complete union with existing groups and configure the clock first. See [RFC:123](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:123) and [bindings.rs:155](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings.rs:155).

10. **MINOR — Correct the proposed test expectations and location.**  
    If `h` survives its first callback at 25, its next deadline is 45. At 60 the wheel’s order is **h, f**, not f, h; specify which invocation clears the interval. For a fixed pending deadline, a backward clock step must not **increase** the remaining delay; “does not move backward” is ambiguous for a countdown. See [RFC:109](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:109) and [timers.rs:120](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/stdlib/timers.rs:120).

    The existing borrowed-runtime fixture is under `crates/ibex2-runtime/tests`, not `crates/ibex2`. Its explicit timer-refusal regression must be replaced when D1 lands. See [embedding.rs:639](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/tests/embedding.rs:639).

The seven proposed tests are insufficient. In addition to regressions for the findings above, add:

- Mixed timer/settlement/WebSocket FIFO ordering; exactly one delivery per call; no implicit checkpoint; pre-existing microtasks and checkpoints between callbacks.
- Nested delivery requests from timer callbacks and error handlers; callback scheduling and cancellation of another already-admitted timer.
- Equal deadlines, backward steps followed by new timer creation, repeated admission without delivery, large forward jumps, and zero/sub-microsecond intervals.
- Clock callback locking/thread behavior, invalid values, panic policy, independent contexts, and configuration refusal after timer creation.
- Timer-only sleeping and wake behavior; settling with a future interval and an open socket.
- Error cancellation, host-reporter fallback without `EVENTS`, native exceptions, and continued delivery afterward.
- Borrowed WebSocket echo/close plus denial, reconnect triggered by a timer, detach with queued events, and GC keepalive reconciliation.
- A construction/heartbeat/backoff scenario matching the stated SDK use, with an explicit `Date` shim for expiry. The small timer and echo tests alone do not establish unmodified SDK compatibility.

The direct-clock inventory otherwise supports the intended separation: timer scheduling and Ibex’s performance binding converge on `RuntimeState::now`. Remaining real clocks serve execution budgets, waits, and transport deadlines—for example [hermes_shim.cc:193](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/src/engine/hermes_shim.cc:193), [rustls_http.rs:251](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/transport/rustls_http.rs:251), and [transport/websocket.rs:1720](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/transport/websocket.rs:1720). One distinction should be explicit: **`AbortSignal.timeout` uses JS timers and consequently follows the caller clock**, even when used to cancel fetch; native transport timeouts remain real-time. See [abort.js:160](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/abort.js:160).
