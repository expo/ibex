## Overview

**Ibex** is the JavaScript/TypeScript runtime used by Exact and Snapback: it
embeds Hermes, exposes a host ABI, and aims at web/Node/Bun-compatible runtime
behavior rather than app-framework behavior `[observed]` (`README.md:3-10`).
The Rust crate is still named `exact-runtime` during the transition to the
Ibex repo/product name `[observed]` (`README.md:12-16`; `Cargo.toml:1-11`).

The README records that this repository was split out of the Exact monorepo
under exact LLP 0180 and will be re-homed later `[observed]` (`README.md:12-16`).
The broader extraction rationale (independent versioning, cross-platform CI,
and multiple consumers avoiding a monorepo vendor copy) is inherited from exact
LLP 0180 and is not independently confirmed by code in this checkout
`[inferred]`.

This retrofit corpus uses the following provenance discipline: concrete
mechanism claims are tagged `[observed]` and cite the current source lines;
claims about intent or external history stay `[inferred]` unless a named human
confirmation is added later. This draft set does not use a human-confirmation
provenance tag.

## Architecture / subsystems

- **Rust crate (`exact-runtime`)** — staticlib + rlib crate linked by embedders
  `[observed]` (`Cargo.toml:1-11`). It exports `engine`, `host`, and
  `module_loader` modules `[observed]` (`src/lib.rs:14-21`).
- **Hermes engine bridge (`src/engine/*.cc`)** — C++ compiled by `build.rs`
  through `cc`, with `hermes_runtime.cc`, `hermes_bootstrap.cc`, and subsystem
  shims listed explicitly `[observed]` (`build.rs:711-781`). It creates Hermes
  runtimes, installs JSI host functions, evaluates JS/HBC, and pumps the event
  loop (see [LLP 0003](./0003-hermes-engine-bridge.explainer.md)).
- **Host ABI (`src/host`)** — the Rust-side host singleton, capability manager,
  file/SQLite/env/random helpers, and module resolver behind the `ex_host_*`
  callbacks `[observed]` (`src/host/mod.rs:14-23`;
  `src/host/abi.rs:578-789`). The public embedding boundary is mapped in
  [LLP 0002](./0002-host-embedding-abi.spec.md).
- **Module loader + builtins (`src/module_loader`, `src/builtins`)** — a
  generated builtin manifest is included from `OUT_DIR`, then used to build a
  specifier-to-source registry `[observed]` (`src/module_loader/mod.rs:58,
  67-70, 1047-1070`). The builtin authoring surface is `modules.ts`,
  `src/builtins/*.js`, and selected runtime JS files.
- **Embedded JS runtime layer** — generated artifacts are committed under
  `vendored-generated/`: the builtin manifest, transformed builtins, and the
  shared runtime bundle `[observed]` (`vendored-generated/README.md:11-27`).
  The generators and package scripts live locally under `packages/ibex-devtools`
  and `packages/ibex-runtime-js` `[observed]` (`package.json:8-14`;
  `packages/ibex-devtools/package.json:7-29`;
  `packages/ibex-runtime-js/package.json:1-62`).
- **Hermes artifacts** — `build.rs` looks for Hermes headers/libs in platform
  defaults (`linux/`, `ios/Frameworks`, Android Maven/PREFAB extracts under
  `android/`, Windows under `tools/hermes`) or `HERMES_INCLUDE_DIR` /
  `HERMES_LIB_DIR` overrides `[observed]` (`build.rs:172-227`). Android also
  needs React Native's JSI PREFAB headers/libs, overrideable through
  `JSI_INCLUDE_DIR` / `JSI_LIB_DIR` `[observed]` (`build.rs:199-227`). Those
  platform artifacts are separate from the vendored JS snapshot described above.

## Key invariants

- **The default build is hermetic for the generated JS layer.** A plain
  `cargo build` path copies committed `vendored-generated/` artifacts instead
  of running JS generators, while regeneration requires
  `IBEX_REGENERATE_RUNTIME=1` `[observed]` (`build.rs:321-351`;
  `vendored-generated/README.md:3-9`). Missing vendored artifacts fail loudly
  instead of silently regenerating `[observed]` (`build.rs:335-345`). The
  in-code comment cites inherited exact LLP 0086 review F7 for this discipline
  `[observed]` (`build.rs:336-340`).
- **The consumer contract is intentionally narrow.** The README names five C
  ABI functions plus `exact_runtime::host::{install_host, Host}` as the
  dependency surface `[observed]` (`README.md:24-30`). The five C functions are
  declared in `include/exact_runtime.h` (`ex_hermes_create`,
  `ex_hermes_destroy`, `ex_hermes_eval`, `ex_hermes_free_string`,
  `ex_hermes_set_host_call`) `[observed]` (`include/exact_runtime.h:34-65,
  151-156`). Treating that set as semver-major comes from exact LLP 0038 and is
  therefore inherited rather than proven by code here `[inferred]`.
- **Crypto is platform-dependent, and the reduced profiles are uneven.** macOS
  and iOS compile the non-Windows crypto shim with CommonCrypto/Security
  available `[observed]` (`src/engine/hermes_runtime_crypto.cc:23-44`);
  iOS always defines `EXACT_NO_OPENSSL` and `EXACT_PLATFORM_IOS` `[observed]`
  (`build.rs:817-823`). Windows compiles `hermes_runtime_crypto_windows.cc` and
  defines `EXACT_NO_OPENSSL` `[observed]` (`build.rs:729-765`). Linux defines
  `EXACT_NO_OPENSSL` unless the `openssl-crypto` feature is enabled
  `[observed]` (`build.rs:824-831`). The Linux default profile is now
  OpenSSL-free at compile time for the reduced surface: it uses portable
  MD5/SHA-1/SHA-2, HMAC, PBKDF2, scrypt, and HKDF helpers while leaving AES and
  asymmetric/key import-export functions to the `openssl-crypto` profile
  `[observed]` (`src/engine/hermes_runtime_crypto.cc`). Linux therefore has two
  intentional profiles rather than a single full platform-crypto backend.
- **Target-platform support is uneven.** `build.rs` has explicit handling for
  macOS, iOS, Android, Linux, and Windows, but no first-class tvOS branch
  `[observed]` (`build.rs:804-1224`). Android cross-compiles with Hermes/JSI
  Android artifacts, vendored OpenSSL, and vendored curl/libz for native
  fetch/WebSocket `[observed]` (`Cargo.toml:79-83`; `build.rs:933-949,
  1106-1172`). [LLP 0001](./0001-target-platforms-and-ci-matrix.rfc.md) records
  the desired platform matrix and the remaining tvOS gap.
- **Linux runtime backends now have an explicit native profile.** The platform
  backend audit records libcurl as the supported Linux Fetch/WebSocket backend,
  POSIX/Linux filesystem and socket choices, OS info behavior, and remaining
  platform gaps `[observed]` ([LLP 0008](./0008-platform-backend-parity-audit.research.md)).
