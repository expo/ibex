**M1 — MATERIAL: The proposed drive flag does not enforce the borrowed cycle’s no-nesting contract.**
D5 releases the flag when `deliver_one` returns, before the caller’s post-checkpoint. A promise reaction executing in that checkpoint can call a caller-provided native function that calls `deliver_one` again. The flag is clear, so another host task runs inside the checkpoint, before its remaining microtasks. The same hole exists during the pre-checkpoint.
This contradicts [LLP 0058.000.000:463](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:463), which requires the post-checkpoint before another reservation and prohibits driving whenever the driver is not Idle. The owning pump holds its guard across both checkpoints at [hermes_shim.cc:537](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/src/engine/hermes_shim.cc:537).
Having the borrowed caller acquire the same flag around its cycle is not sufficient: D5 would then reject that caller’s legitimate step 3. Specify a complete cycle guard and how delivery operates within it, while preserving the standalone storage-delivery API. Also explicitly reconcile throwing a nested-delivery error with §8’s wakeup/defer rule.
The owning runtime does **not** inherently double-acquire the flag under the proposed change: it calls `ibex2_take_task` and then `fire_timer`/`deliver_event`/`settle` directly at [hermes_shim.cc:555](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2-runtime/src/engine/hermes_shim.cc:555), bypassing `deliver_one`.
**M2 — MATERIAL: D6 still equates task reservation with delivery commit without amending the conflicting contract.**
[r2:152](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:152) commits interval rescheduling when the task is taken. But [LLP 0058.000.000:453](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:453) explicitly says reservation is not an irreversible timer transition; adapter revalidation and commit follow it. [That spec’s timer paragraph:555](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0058.000.000-rust-capability-context-and-engine-adapter.spec.md:555) also requires failed admission to leave the timer eligible.
The relevant code path is:
- Both drivers call [boundary_abi.rs:1230](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/boundary_abi.rs:1230).
- That calls `RuntimeState::take_task`.
- The FIFO removal happens at [task.rs:1164](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1164), while the **subscription registry mutex is held**, including for timer tasks.
- The borrowed adapter subsequently dispatches at [install.cc:2313](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/bindings/install.cc:2313); the owning pump has its separate dispatch path.
Consequently, inserting `now()` at the existing removal point violates D3’s no-lock callback contract. Implementing rescheduling only in `deliver_one` misses the owning pump entirely.
This is implementable, but the RFC must choose and describe the common transition: either retain separate reservation and commit, or explicitly amend §8 so an appropriately validated take is the timer commit. Specify cancellation and failed-admission disposition around that transition. Sample the clock outside the subscription and timer locks.
**M3 — MATERIAL: The unconditional repeat floor contradicts the timer specification that r2 leaves unchanged.**
[r2:157](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:157) applies a 4 ms floor immediately after the first delivery, while describing it as HTML’s nesting clamp. Its own parenthetical acknowledges that the HTML threshold is reached later.
For example, a 1 ms interval delivered at caller time 1 has its next occurrence at 5 under D6. That is an intentional change to the early interval occurrences, including with the default `Instant` clock. [LLP 0059.000:205](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0059.000-v1-api-specifications.spec.md:205) still promises HTML clamping.
Either implement the stated HTML nesting rule or explicitly amend §3.2 to document Ibex’s earlier, unconditional repeat clamp. Rescheduling outside admission already removes the single-admission infinite loop; that fix does not itself require this compatibility change.
**M4 — MATERIAL: Test 7 contradicts the clock contract and is not a sound deadlock regression as stated.**
[Test 7:202](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:202) requires the clock to invoke timer scheduling, although [D3:99](/Users/ccheever/projects/ibex2-borrowed-timers/llp/0071-timers-and-a-clock-for-a-borrowed-runtime.rfc.md:99) prohibits calling back into this runtime.
Moreover, scheduling calls `now()` at [task.rs:1011](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1011). After moving that call outside the mutex, an unconditional scheduling clock recursively calls itself until stack exhaustion. Removing the mutex does not make this callback safe, and catching ordinary unwinding panics is not a stack-overflow containment strategy.
Replace this with a bounded, explicit lock-observation test. If deliberately testing prohibited reentry, specify a one-shot recursion guard and distinguish that diagnostic from supported callback behavior.
The remaining implementation checks are as follows:
- **Integer samples and atomic maximum are feasible.** `2^53 × 1000` fits in `u64`. Store the maximum in integer microseconds and compute the nonnegative **integer difference before converting to milliseconds**. Retaining the current absolute-`f64` `next_deadline()` subtraction at [task.rs:1041](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/task.rs:1041) would not implement D3. Avoid converting the accepted integer back to milliseconds and then re-quantizing it through the existing wheel API.
- **First-read sealing is feasible.** Source selection and sealing must be one synchronized decision, with invocation of the selected callback afterward, outside the synchronization. Define the initial previous sample—presumably zero—for an invalid first reading.

The current dispatch at [boundary_abi.rs:614](/Users/ccheever/projects/ibex2-borrowed-timers/crates/ibex2/src/boundary_abi.rs:614) provides no such containment. The trait object does not promise unwind safety, so the implementation must deliberately handle that boundary.
